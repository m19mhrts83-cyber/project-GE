**LINE（CHRLINE sync + オープンチャット・パートナー取り込み向け）**:

```bash
# 正本: CHRLINE-Patch（.venv-patch）経由。旧 .venv（2.6.0b18）は Square 不安定のため使わない
cd ~/git-repos/line_unofficial_poc && ./run_patch.sh chrline_yoritoori_inbox_fetch.py --allow-qr-login --discover-thread-mids-dry-run
```

- **推奨**: 上記 **統合スクリプト**で sync（Tcell + LEAF）とオープンチャット同期を **1 プロセス・厳密に 1 回の QR**で実行する。個別実行は下記参照。
- **添付（2026-07〜）**: sync 追記時に画像・動画・音声・ファイルを `1.受信添付(Stock)/YYYY-MM-DD/` へベストエフォート保存。失敗時は stderr にログ、本文は `[画像]`/`[動画]`/`[音声]`/`[ファイル]`。スタンプ・公式エクスポート経由のバイナリは対象外。
- **QR 方針（2026-07-19）**: プロセスあたり **最大1回**。sync 後にセッションが死んでも **第2 QR は出さない**（open-chat をスキップし stderr に `no_second_qr`）。オプチャだけ取り直すときは別プロセスで `--skip-sync --allow-qr-login`。
- **定常ヘルス**: 統合スクリプトは sync 成功後に **LINE本文ヘルス（定常）** を標準出力（MDプレースホルダー件数・前回比・retryキュー・textual率）。前回値は `LINE_UNOFFICIAL_AUTH_DIR/.chrline_line_health_last.json`。単独実行: `.venv/bin/python chrline_line_health.py`（ヘルスは認証不要）
- sync には **案D改善パラメータが既定**（`--skip-sync-improved-params` で無効化）。`--no-line-health` でヘルス出力オフ。
- **スレッド heal / catchup（既定 ON）**: 統合スクリプトは `--threads-only` フェーズで **`--heal-degraded-threads`** と **`--thread-catchup-pages 8`** を付与（degraded+sync_token 空のバックオフ解除→再試行）。無効化: `--no-heal-degraded-threads`。復旧 run 時は `--thread-catchup-pages 10` 推奨（下記 §4）。
- QR 再認証が必要な場合、**別プロセスで sync と open-chat を別々に走らせると QR が複数出る**ため、パートナー確認では統合スクリプトを正とする。
- **QR 再認証**: `build_logged_in_client` の既定は **QR を出さない**（`allow_qr_login=False`）。**やり取り確認など対話で取り込むときだけ** `--allow-qr-login` を付ける（保存トークンが有効ならフラグは実質ノーOp）。表示は **URL/IMG を1セットだけ**（chunk 更新のたびに出さない）。失効トークンは自動削除し有効1件のみ保持。
- バックグラウンドのヘルスチェック（`launchd/open_chat_healthcheck_runner.sh` → `chrline_list_open_chats_poc.py`）はフラグなしのため、**トークン切れ時に QR で埋もれない**（終了コード 2 で失敗扱い・通知）。
- プリセット: 既定 `line-default`（**Tcell はグループ「キャラメル管理G」のみ**＋ LEAF グループ）。`--sync-preset` で変更可（`tcell-both` / `tcell-yuki` / `leaf-grandole`）。
- 前提: `LINE_UNOFFICIAL_AUTH_DIR`（**未設定なら** `line_unofficial_poc/.line_auth_local` に自動。クラウド同期パスは非推奨）。
- セッション失効時は QR 再認証が必要（非公式 API の制約で省略不可）。`LINE_CHRLINE_AUTO_OPEN_QR=1` で QR 画像を自動表示。

- **`chrline_yoritoori_inbox_fetch.py`**（正本は `./run_patch.sh` 経由）は **LINE sync → オプチャ（メイン → discover → スレッド）** の順で **厳密に 1 回の QR** を実行（`--open-chat-first` でオプチャ優先）。フェーズ間は **無 QR** でセッション再確認し、死んでいれば open-chat / スレッドをスキップ（`no_second_qr`）。
- 新規スレッドはメイン差分の `--discover-thread-mids-dry-run` で候補検出 → ユーザー確認後 YAML 追記 → 初回のみ `--init --no-main` でバックフィル。
- 閉鎖済みを再スキャンしたいときだけ `--threads-only --include-closed-threads`（通常は不要）。
- 終了時: `# thread diff: YAML登録 503 件のうち取得可能 37 件を対象（閉鎖済みスキップ 466 件）` のような行が stderr に出る。
- スレッド同期終了時: `# thread sync: total=… ok=… skipped=… appended=…` と `# thread heal:`（heal 実施時）を stderr に出力。パートナー確認報告に **必須**。

- **再ログイン**: オープンチャット同期でも `--allow-qr-login` を付けたときだけトークン失効時に QR を開始する。付けずに実行した場合は終了コード 2 で終了するので、意図しない時間帯に QR が出ない。

- ルート YAML: 環境変数 `LINE_OPEN_CHAT_ROUTES_YAML`（未指定時 `open_chat_routes.yaml`）
- **認証はトーク同期と共有**: `chrline_open_chat_to_md.py` も `chrline_sync_to_yoritoori.py` も同じ `LINE_UNOFFICIAL_AUTH_DIR` と `chrline_client_utils.build_logged_in_client` を使う。**別ディレクトリに分けると QR ログインが冗長に増えやすい**。
- **`.tokens/`**: 有効トークンは **1 件のみ保持**（失効分は試行時に自動削除）。再認証後は `persist_auth_token` で保存。
- **クラウド同期パス**: `LINE_UNOFFICIAL_AUTH_DIR` が OneDrive 等を含むと警告（セッション競合で QR が増えやすい）。未設定なら `line_unofficial_poc/.line_auth_local` 既定を推奨。
- QR・`LINE_CHRLINE_AUTO_OPEN_QR`: 上記「LINE（CHRLINE sync）」と同じ。セッション失効時の QR 自体は非公式 API の制約で省略不可。
- （任意）疎通監視: `line_unofficial_poc/launchd/open_chat_healthcheck_runner.sh` … 失敗時に通知し再ログインを促す。

## グルコン報告（活動・成果）

Dashboard: `/glucon`（タスク → グルコン報告）

開催日は kamiooya-qa の `神大家4.グルコン` レッスン標題から取得。提出期限 = 開催日 − 10 日。次サイクルは **開催日の翌日** から表示（未掲載なら前回+約30日）。

定常の本線は **活動報告**。集約期間は **前回活動の `covered_to` 翌日〜今回提出期限**（初回後の起点は 2026-08-11）。成果報告は購入・満室化などの大きな区切りのときだけ使う。

WeStudy の最終「コミュニティに登録する」はユーザーが押す。押したあと `/glucon` の **WeStudy で投稿した** でダッシュボードを `posted` にする。

### 成果報告の対話型フロー（例外・大きな区切り）

神・大家さんポイントが貯まるのは **成果報告**のみ。大きな実践成果がある月だけ下のステップを使う。

1. **対象期間を指定** — 前回投稿の `covered_to` 翌日〜今日が既定。月をまたいだまとめも可（Journal sync は直近約90日が実用範囲）
2. **① 事実だけで下書き** — Journal／やり取り／入退去から推測なしの事実リスト（出典・成果候補タグ付き）。空室→入居日数（早期フラグ）も注入
3. **② 質問に答える** — 苦労・工夫・入会前の状態など 3〜5問（スキップ可）
4. **③ 最終稿** — コミュニティ型（`■【カテゴリ】`＋項目行＋`所感等`＋`■Before(入会前)`／`■After(入会後)`）
5. **聞く／直す** — 画面内パネルで相談・差分反映
6. 保存 → WeStudy 投稿（確認モーダル）。投稿時に `covered_from`/`covered_to` を履歴保存 → 次回の既定期間になる

`/glucon` 下部に **これまでの報告**（月ごと折りたたみ・本文全文）と **継続とポイント**（活動の連続月・報告回数グラフ・成果の神大家ポイント目安）がある。目安点は投稿キュー投入時に `payload.scoring` へ保存（無い過去行は本文から再計算）。連続は活動が `posted` または `skipped` の月。運営採点の保証ではない。

「活動の下書きを作る」が定常。前回投稿本文は再掲せず、進展だけを書く。大きな成果は活動で1行、詳細は成果パネル。

### 次月報告メモ

`/glucon` の日程ヘッダ直下。今月は見送り・次月ネタに回すことを `glucon_carry_memos` に残す（下書きの `period_key` とは独立）。

- 退避した周期の下書き生成には**入れない**。翌周期以降の活動／成果生成へ自動注入
- 未実施なら成果本文に書かない（完了を断定しない）。投稿しても自動完了しない。「今回使った」で閉じる
- 初回シード: スマートロックまとめ資料の見直し共有（2026-08 退避 → 2026-09 から注入）

初回など **90日を超える長期まとめ**は、Mac の Journal／やり取り／過去投稿 CSV をスレッドで下書きしてから `/glucon` に貼るのが効率的。
