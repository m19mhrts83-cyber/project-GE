# 個別業務の工数をJARVIS Dashboardで把握する運用

2026-10-29 松野さんの意図確認。本人用の内部管理の改善で、運営へ共有するページや運営へ請求する新規開発案件ではない。2026-11-01、PR #206で項目別実行履歴・質問回答・時間区分の閲覧を `/kamiooya/history` へ実装し、本番表示と検索を確認。PR #207で画面からの追記・訂正理由付きの時間見直し・質問回答も追加し、本番保存とCLIへの双方向取り込みを確認。以下の超過予測等は引き続き表示要件であり、自動計測・常時同期は未実装。

## 目的

個別業務を進める途中で、どれくらい時間を使ったか、今の進捗で最終的にどれくらいになるかを把握し、必要な相談をAIから促す。契約は概算見積もり・実績精算、概算工数を2割以上超える見込みで再承認する現在の方針を維持する。

## 記録と表示

- 案件単位で、承認工数、累計実績、残作業見込み、完了見込み、見込みの根拠、最終更新日時を表示する。
- 実績の消化率と、完了見込みによる超過率を別々に表示する。工数消化率を作業の進捗率と呼ばない。
- 「実績が見積超過」「完了時に超過しそう」「2割以上の超過見込み」を区別し、同時に該当する場合は併記する。
- 例: 承認10h、実績6h、残り7hなら、実績消化60%、完了見込み13h、見込み超過30%、再承認相談が必要。これは説明例で、実在の案件実績ではない。
- 残工数が不明なら「未評価」、推計実績なら「未確認を含む」、更新されていなければ最終更新日時と記録確認の案内を出す。
- 警告の理由、発生日時、松野さんへの提案、対応状況、再承認証跡を履歴として残す。表示だけで履歴を失わない。
- 再承認時は当初工数と改定版を保持する。承認済みとは相手の承認証跡がある状態で、AIの提案だけでは切り替えない。

## 記録元と連携候補

AIが作業の区切りで、当該案件フォルダの `工数管理/` に記録する。テンプレートは神大家AI推進案件の `工数管理/工数管理_案件テンプレート.md`。全チャット履歴を毎回解析せず、最新の案件記録と差分を確認する。推計時間と本人確認済み実績を区別する。

2026-11-01以降の項目別履歴は `work_history.json` を正本とし、同名MDを自動生成。エージェントが `scripts/jarvis_kamiooya_work_history.py --push` で認証済みDashboardへ投影する。運用とコマンドは `docs/神大家運営_作業項目と実行履歴_20261101.md` を参照。

現在のDashboard `/kamiooya` は `apps/jarvis-dashboard/app/kamiooya/page.tsx` から `TriageKanbanLane` を表示する構成。まず、この本人用ページへ工数の要約を載せる方法を検討する。既存ページの認証を維持する。

OneDrive上のMarkdownは、そのままクラウドのDashboardから読めない。既存の認証済みデータ連携・保存先を確認して、案件記録の必要項目だけを同期する。会員情報、会話全文、ローカル絶対パス等を表示データへ不要に含めず、公開静的ページへ契約情報を置かない。

表示更新の契機は作業記録の更新。AIの未起動時にも新しい実績を自動取得できるとは説明しない。自動集計・同期の実装は既存構成を確認して進め、表示済み・稼働済みと誤って報告しない。
