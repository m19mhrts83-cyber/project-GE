# 神大家Q&A 改善(1)〜(3) ブランチ一覧と段階公開の決まりごと（2026-11-10）

## 段階公開スイッチ（共通部分）

各機能は `qa_feature_flags` テーブルの1行で、段階を切り替える。判定はサーバー（raimo-auth の `/features` と `requireFeature`）で行う。

| 段階 | 見える人 | 使う場面 |
|---|---|---|
| off | 誰にも見えない | 初期値。見送りになったとき |
| owner | `owner_ids` の人（松野さん）だけ | 運営の了承前に先行で作って確かめる |
| reviewers | `owner_ids`＋`reviewer_ids`（今村さん・目黒さんなど） | 了承後、運営に見て比べてもらう |
| all | 会員全員 | 確認が取れたあとで反映する |

- 管理者かどうかでは判定しない。了承前は、管理者である運営にも見せない。
- 見える人の画面には「確認用」バーが出る。「新しい版で見る」で今の版と比べられ、「会員として見る」で管理メニューを隠して一般会員の見え方を確かめられる。
- 切り替えは Miss Lemon が SQL で行う（松野さんの手作業なし）。例: `update qa_feature_flags set stage='owner', owner_ids='{<松野さんのログインメール>}', updated_at=now() where feature='answer_feedback';`
- DB の変更は追加だけにする。全員に開く前に、毎回会員種別ごとの見え方を確認する。

## 決まりごと

1. 項目ごとにブランチと下書きPRを持つ。PR一覧が状態の一覧になる。
2. 共通部分を先に main に入れる（スイッチは全部 off なので会員には何も変わらない）。各項目は共通部分の上に作る。
3. 各項目は、作り終えたら main に入れて `owner` で本番に出し、松野さんが本物の画面で確かめる。運営の了承が出たら `reviewers`、確認が取れたら `all`。
4. 了承が出なかった項目は main に入れないか `off` のままにし、ブランチと PR は消さずに残す（PR に「見送り」と書く）。
5. main が更新されたら、確認に出す前に Miss Lemon がブランチを最新の main に合わせる。
6. 本番反映は GitHub Actions「kamiooya-qa release」（migration・Edge Function）。Raimo の画面（app.js / index.html）の公開は Mac の `scripts/kamiooya_qa_release.py --raimo-front` が必要。

## (3) 名簿の毎日取り込み（Mac launchd、2026-11-11〜）

- 毎朝 6:00 JST に `scripts/kamiooya_roster_sync.py` を実行し、`qa_roster_hashes` を全件入れ替える。Mac が眠っていた日は、起きたとき（またはログイン時）に1回。その日に成功済みなら何もしない。
- 名簿シートを開けるのは estate アカウントだけなので、GHA ではなく Mac で動かす（認証は `westudy_common/google_workspace_auth.py`）。
- `~/git-repos` の main は使わない。専用 worktree `~/.jarvis_worktrees/kamiooya-roster` を毎回 `origin/main` に合わせてから実行する。
- 入れ方: `zsh launchd/install_kamiooya_roster_sync_launchd.sh`（label `com.matsunoma.jarvis.kamiooya-roster-sync`）。止めるときは `KAMIOOYA_ROSTER_SYNC_DISABLE=1` か `launchctl bootout`。
- ログ: `~/Library/Logs/kamiooya_roster_sync/sync.log`（件数と OK/FAIL だけ。名前・会員番号は書かない）。Google の一時エラーに備えて3回まで再試行。2回続けて失敗したら Slack #ops に1回知らせる。
- 確認: `select row_count, synced_at from qa_roster_meta;`

## (4) 質問ランキング＋講座テーマ案（2026-11-11〜）

- 運営分析の「質問ランキングと講座テーマ案」枠。スイッチ `ranking_themes` が見える管理者だけに出る（API は raimo-auth の `/admin/ranking-themes/list`・`/decide`）。
- 毎週月曜 6:00 JST に GitHub Actions「course-theme weekly」が `scripts/course_theme/weekly_round.py` を実行。DB 関数 `qa_theme_source_digest(120)` の集計（百KB前後）と過去の判断を Gemini に渡し、似た質問のまとまりランキング（最大20）とテーマ案5つを `qa_theme_rounds` に入れる。
- 運営が 採用／直して採用／不採用＋理由 を残す（`qa_theme_decisions`）。次の回はその判断を読んで案を作る（ループウェア）。
- 手動で回を作るときは Actions の workflow_dispatch。確認: `select id, created_at, jsonb_array_length(themes) from qa_theme_rounds order by created_at desc limit 3;`
