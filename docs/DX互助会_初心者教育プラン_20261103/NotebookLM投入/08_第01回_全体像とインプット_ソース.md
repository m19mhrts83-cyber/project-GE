# 第01回：AIに伝える・一緒に進める・見える形にする

更新：2026年11月4日。初心者向け・月1回30分講座の初回導入。今回の方針は、従来のメール実習版より優先する。時間配分・例文は講師向けの提案。

## 今日のゴール

AIを使う仕事の流れを知り、短く頼んで、結果を見て1回直す。うまく伝わった頼み方を、次も使えるメモとして残す。

将来は、既存の資料やアプリをAIと相談して直せるようになりたい。その入口として、今日は「伝え方」を練習する。

## 1. 最初に、仕事の全体像を見る

仕事を「インプット→プロセス→アウトプット」の3つに分けて考える。

- インプット：目的と材料を渡す。誰として、何を参考に、何をしてほしいかを伝える。音声で話してもよく、再利用する内容はMarkdownに残せる。
- プロセス：AIと一緒に進め、途中の成果物を確かめる。松野さんはCursorを軸に、参照するファイルと作業範囲を伝え、小さく作って、見て、直して、保存している。
- アウトプット：誰に何を伝えるかに合った形へ整える。松野さんは、Markdownでまとめたアイデアと必要な調査結果をNotebookLMへ渡し、デザインを指定してスライドにする。人への説明にも、自分の理解にも使う。

この講座の資料作りも同じ流れ。考えを音声で話す→AIと整理して原稿をファイルに残す→NotebookLMで説明資料へ整える。今日はこの全体像を見たうえで、最初のインプットを詳しく練習する。

CursorやNotebookLMは松野さんの実践例。毎回すべてを使う必要はない。メール返信なら文章、管理業務なら表など、目的に合う成果物を選ぶ。

### それぞれの工程で決めておくこと

- インプットの型：役割・参考材料・依頼。必要なら守ってほしい条件も加える。
- プロセスの型：参考を確認→小さく作る→人が見る→修正を頼む→保存する。
- アウトプットの型：読む人・用途・形式・確かめる点。スライドなら内容と出典、文章なら事実と口調を確認する。

「型」は最初から長い指示文を作ることではない。仕事の目的・材料・仕上がりを、途中で見失わないために決める。

## 2. バイブコーディングへの入口

バイブコーディングは、作りたいものを自然な言葉で伝え、AIの作ったものを動かし、結果を見ながら直すソフトウェア開発の進め方として紹介する。

今回練習する「頼む→見る→直す」は、その先のアプリ修正にもつながる習慣。初回の文章整理自体をアプリ開発と呼ぶ必要はない。後の講座では、既存HTMLの一部修正、小さなアプリの改修、確認と履歴管理へ進む。

## 3. Markdownは、AIと共有できる整理されたメモ

Markdownは、普通の文字に見出しや箇条書きの印を付ける書き方。`.md`は、そのような文書によく使うファイル名の末尾。

初回は3つだけ見る。

```markdown
# AIへのお願い
## 参考にしてほしいこと
- 対象はAIを使い始めた人
- 1回30分の講座
## 作ってほしいもの
- やさしい説明を3項目
```

`#`は大きな見出し、`##`はその下の見出し、`-`は箇条書き。Cursorで元の文字とプレビューを講師が見せる。全部の記号を覚える必要はない。

役に立つのは、依頼と材料を分け、直し、保存し、ほかの人にも渡せること。`.md`にするだけでAIが正しく答えるわけではない。普通のチャットでも同じ整理は使える。ファイルを保存したら、参照対象としてAIへ渡したかも確認する。

## 4. プロンプトは、一度で完成させなくてよい

プロンプトは、AIへのお願いや質問のこと。

講師の経験として、以前は細かな項目を先に決めて指示文を作ることを学んだ、という話から入る。現在の講座では、必要なことを短く伝えて始め、出てきたものを見て、足りないところを追加する方法を勧める。

「プロンプトエンジニアリングが不要になった」とは説明しない。目的、参考材料、守る条件、ほしい仕上がりは今も大切。最初から全部を盛り込もうとせず、対話で具体化し、うまくいった指示を最後に整理して残す。

比較用の講座内例：

- 最初：「この説明メモを、初心者向けに3項目で短くまとめて」
- 結果を見て：「専門用語を減らして、各項目に身近な例を1つ入れて」
- 最後に：「今回うまくいった頼み方を、次も使えるメモにまとめて」

これは説明用の例であり、講師の過去の検定問題・実話ではない。検定作成時の具体的なエピソードは、本人が確認した内容を口頭で補う。

## 5. 伝え方は3Rを手掛かりにする

前回の資料と同じ意味で使う。

- Role（役割）：誰として答えてほしいか。例「初心者に教える講師として」
- Reference（参考）：何を読んでほしいか。例「この説明メモを参考に」
- Request（依頼）：何をしてほしいか。例「AI活用の流れを、3つの見出しで短くまとめて」

英単語の暗記が目的ではない。「誰として・何を参考に・何をしてほしい」が伝わればよい。仕上がりの長さや形式はRequestに添える。

### 再利用するためのMarkdown見本

```markdown
# Role：役割
初心者にやさしく教える講師として答えてください。

# Reference：参考
このチャットで共有した「インプット・プロセス・アウトプット」の説明メモを参考にしてください。
対象はAIを使い始めたDX互助会メンバーです。

# Request：依頼
AIを使う仕事の流れを、3つの見出しで短くまとめてください。
各見出しに身近な例を1つ入れてください。
不明な内容は、事実として付け足さないでください。
```

実際のファイルを使うときは「このチャットで共有した説明メモ」を、渡したファイル名に置き換える。渡していないファイルを読んだ前提にしない。

## 6. 音声入力で、対話を続けやすくする

話して入力すると、最初の相談も追加の修正も伝えやすくなる。AIへの指示だけでなく、思いつきや日常のメモにも使える。

アプリ内の音声機能に加え、OSの音声入力が使える場合もある。まず自分のPCやスマートフォンで使える方法を試す。対応や操作は機器・OS・アプリで違うので、講師は事前に入力欄で試しておく。

Typelessのような専用アプリは、入力を便利にする選択肢。無料枠と有料プランがあり、有料契約を初回の参加条件にしない。料金や上限を紹介する場合は当日の公式情報を確認する。

### Typelessを使う利点：話した内容を整え、いつもの言葉を覚える

アプリをまたいで入力できる利便性に加え、次の2点を補足する。

- **話した内容を読みやすく整える。** 「えーと」などのつなぎ言葉や不要な繰り返しを取り除き、途中の言い直しを反映し、箇条書きなどへ整える。考えながら話しても、意図を伝えやすい文章になる。内容を短く要約したい場合は、対象の文章を選び、Ask anythingで「短く要約して」と頼む使い方もある。通常の音声入力時の整文と、依頼して行う要約は分けて説明する。[公式の機能説明](https://www.typeless.com/)
- **修正した言葉を覚え、同じ誤変換を減らす助けになる。** 音声入力後に単語を直すと、好みの表記を認識して辞書のAuto-addedへ追加する仕組みがある。人名・業界用語などを手動登録することもできる。使う言葉に合わせて育てていける。[公式の辞書説明](https://www.typeless.com/help/quickstart/history-and-dictionary)

本人の言い回しや文章の調子に合わせるPersonalizationもある。[公式の説明](https://www.typeless.com/help/quickstart/personalization)

講師の一言：「考えながら話した内容を読みやすく整え、よく使う言葉の表記も覚えてくれます。入力や手直しの負担を減らして、AIとのやり取りを続けやすくする道具です。」

説明用の例：「えーと、会議は火曜日、じゃなくて水曜日の15時です」→「会議は水曜日の15時です」。これは言い直しの反映を示す想定例で、今回の実機検証結果ではない。固有名詞・数字・否定は、整えられた文章でも送信前に確認する。

### 7分の実践

1. 講師が説明メモを共有し、今使えるチャットAIを開く。
2. 本人が話す。「初心者向けAI講座の講師としてお願い。この説明メモを参考に、AI活用の流れを3つの見出しで短くまとめて」
3. 入力された文字を確認する。固有名詞・数字・否定の聞き違いを直してから送る。
4. 出てきた文章を読み、本人が1つ修正を頼む。例「専門用語を減らして、身近な例を1つずつ入れて」。
5. 最初と修正後を見比べ、使えそうな説明と頼み方をメモに残す。講師がMarkdownでの保存例を見せる。

音声入力を使えない人は手入力や例文のコピーで同じ練習をする。実際の機密メールや個人情報を教材に使わない。

## 7. 今日の持ち帰りと次回

持ち帰るのは、修正前後の短い説明と、再利用できる3Rの依頼メモ。

できたかどうかは「3Rで依頼できる」「結果を見て1つ修正できる」「メモの保存場所が分かる」で確認する。

月の間に5分だけ、日常のメモで同じやり方を試す。話す→確認→1回直す→良かった頼み方を残す。宿題の提出は必須にしない。
