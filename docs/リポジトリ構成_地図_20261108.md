- **リポジトリは1つ**（GitHub `project-GE` ＝ Mac の `~/git-repos`）。アプリ・自動処理・資料・AI社員の定義が全部入っている。

## Git の決まりごと（これだけ守れば迷わない）

| 言葉 | 意味 |
|------|------|
| リポジトリ | フォルダの木 ＋ 全部の変更の記録帳 |
| コミット | 変更1回分の記録（いつ・誰が・何を・なぜ）。リポジトリ全体のその時点の写真 |
| ブランチ | 本番（`main`）を触らずに試すための枝分かれ |
| PR（プルリクエスト） | 「この枝を main に合流させていいか」を確かめる場。テスト（GitHub Actions）もここで走る |
| マージ | 枝を main に合流させること。= 本番に出ること |
| push / pull | 手元 → GitHub に送る / GitHub → 手元に受け取る |

1. **`main` ＝ 本番**。main に直接書き込まない（AI に頼む作業はすべてブランチ → PR）。
2. **1つの目的 ＝ 1ブランチ ＝ 1PR**。AI のスレッド1本がちょうど1PR。小さいほど見やすく、戻すのも簡単。
3. **PR のテストが緑になってからマージ**。Vercel の「失敗」表示は上限のせいのこともあるので、中身は GitHub Actions の結果で判断する。
4. **マージで終わりにしない**。本番に入ったか・何が変わったかを確かめて報告するまでが完了。
5. 手元（Mac）で作業を始める前に `git pull`（GitHub の最新を受け取る）。

## 動かしてはいけないパス（実行契約）

次をネストしたりリネームすると、Python の `REPO` 解決・launchd 絶対パス・GHA・運用コマンドが一斉に壊れる。

| パス | 主な依存 |
|------|----------|
| `scripts/` | 約300本が「親＝リポルート」前提 |
| `config/` | 多数スクリプトが `REPO / "config"` |
| `launchd/` | plist に `REPO_DIR` を焼き込み |
| `215_kamiooya/` | パートナー取込・WeStudy・Zaim・GHA |
| `line_unofficial_poc/` | CHRLINE・常時監視・`_REPO_ROOT` |
| `apps/` | Vercel `rootDirectory`（既にネスト済み・内部再編は別 PR） |
| `.env.jarvis_private` · `.jarvis_state/` | ルート固定 |

本整理（地図優先）では **上記は移動しない**。見た目の整理は地図と `archive/` への散在退避のみ。

## CLAUDE.md / コーディング文書の分担

**コーディング関連は git-repos 側が正。社員フォルダは役割・合図・権限・報告に寄せ、手順はリンクする。**

規格: [`30_共通Agentフォルダ規格_BCP_20261017.md`](AIエージェントチーム/30_共通Agentフォルダ規格_BCP_20261017.md)  
（社員 `scripts/` は薄いラッパ。本線は `~/git-repos/scripts`）

| 置き場 | 書くこと | 書かないこと |
|--------|----------|--------------|
| リポ直下 `AGENTS.md` / `CLAUDE.md` | monorepo 全体の規約・Cloud で動くアプリ・神大家見積ゲート | 社員ごとの合図・Slack 報告型 |
| `apps/*/README` · `docs/運用コマンド一覧.md` · `.cursor/rules/*.mdc` | 起動・デプロイ・CLI・パス・復旧 | 「この社員がいつ動くか」 |
| `docs/AIエージェントチーム/.../CLAUDE.md` | 役割・合図・実行権限・報告先・停止条件・`flow.md` | 長い実装手順の複製 |
| Drive `★AIエージェントチーム` | git からの写し（閲覧） | ここだけ直して git に戻すこと |

二重管理を避ける:

1. 実装・コマンドが増えたら **docs / 運用コマンド / ルール**を先に更新
2. 社員 `CLAUDE.md` は「何をする係か」と **正本への相対リンク**だけ足す
3. 社員専用の薄いラッパだけ社員 `scripts/` に置いてよい
