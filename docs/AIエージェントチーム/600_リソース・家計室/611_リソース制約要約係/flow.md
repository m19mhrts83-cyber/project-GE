## 2. コメント（統合する理由）

1. 611 の「使用状況＋頻度の減増」と 813 の「枠を見て代行先を決める」は、同じ使用量の表を読んで同じ週次で動く。別々にすると材料の受け渡しが一段増えるだけ。
2. 固定の代行チェーンは4者運用と合わない。枠が切れてから切り替えるより、作業を出す時点で回し先を決めるほうが「使用量を分散する」目的に直接効く。
3. 材料が無いと判断できない。まず使用量の集計を作るのが先。

## 3. 思い描くフロー（案）

型: 開始トリガー → 経路 → 合流 → 点検 → Slack。**動きは二つ**あり、同じ表を使う。

### 動きA：週次の使用状況リサーチ（材料づくり）

| 段 | 内容 | 担当 |
|---|---|---|
| トリガー | 週次（既存の週次に相乗り。専用スケジューラは増やさない）。Cursor が警告域（既存の閾値 70%）に入ったら臨時 | ルール |

| 報告 | `#ops` に週次サマリー。頻度の変更案は `#consult` | ルール |

### 配車の基本方針（2026-11-05 松野さん共有）

今後の自動化は、**使用量を抑えるために役割を二つに分ける**。

- **作業フローの磨きあげ**: チャッピーの **ChatGPT モード**でやる（フローの確認・コメント・思い描くフローの明確化、エージェント指示づくり）
- **コーディング**: **Codex ほかのエージェントツール**に任せる

配車案は、この分け方を既定にする。割り振り先はまず「磨きあげ＝チャッピー（ChatGPT）」「コーディング＝Codex」で考え、Codex に余裕がないときだけ他のエージェントツール（フライデー＝GenCode、ミスレモン＝Claude Code、ジャービス＝Cursor）へ回す。レビューやお金まわりなど、元々ツールが決まっている仕事（送金・OTP・銀行 IB はジャービス専属）は例外。

### 動きB：作業の割り振り案（配車）

| 段 | 内容 | 担当 |
|---|---|---|
| トリガー | 松野さんが「これ誰にやらせる？」と頼んだとき、または実装系の Todoist タスクが起票されたとき | 松野／ルール |
| 経路1 | 動きAの表で、いまの余裕を読む | ルール |
| 経路2 | 作業の中身を読む（Todoist のタスク、社員フォルダの `TASK.md`） | ルール |
| 合流・判断 | 作業の種類 × 余裕で回し先を決める。目安: フロー磨き・設計＝チャッピー（ChatGPT モード）、コーディング＝Codex、Codex が逼迫＝フライデー／ミスレモン／ジャービスのうち余裕のあるもの、お金まわり＝ジャービス専属。理由を一行付ける | AI（軽量） |
| 引き継ぎ | 回し先ごとに渡し票を `TASK.md` に書く（実行者・完了条件・読むファイル・次の一手・検証結果） | AI（軽量） |
| 報告 | **Slack `#consult` に割り振り案を出す**（作業／割り振り先／理由／渡し票のリンク。末尾に「次の担当」3行）。**松野さんが見て、そのエージェントに指示する**。係は指示しない | 松野 |

### 4点まとめ

- **トリガー**: 週次（動きA）／松野さんの依頼・実装タスクの起票（動きB）／Cursor 警告域（臨時）
- **権限**: 読む＝使用量・Todoist・`TASK.md`／書く＝渡し票（`TASK.md`）と使用量の表だけ。ツールの切替・課金変更・社員の停止・作業の自動起動はしない。頻度の本番変更は松野さんの了承後に Jarvis が反映
- **作業内容**: 使用状況のリサーチと、作業の割り振り案づくり
- **報告**: 割り振り案と頻度案は `#consult`、週次サマリーは `#ops`

AI を使うのは「回し先の判断」と「渡し票の文面」だけ。集計はルールで回し、この係自体が使用量を食わないようにする。

### 自動起動の段階案（2026-11-05 松野さん「自動で起動できるならそうしたい」を受けた案）

起動の道具の候補: GitHub の Issue／コメントで Codex・Claude Code のクラウド実行を呼ぶ、Cursor のバックグラウンドエージェント、GenCode の呼び出し口。どれも「ブランチに下書き PR を出す」ところまでで止められる。成果は必ず人がマージする。

| 段 | 動き | 松野さんの手間 |
|---|---|---|
| 1（今の案） | `#consult` に配車案を出す。松野さんが各ツールに指示 | 指示を出す |
| 2 | 配車案に ✅ のリアクションが付いたら、係が回し先を自動で起動する | ✅ を押すだけ |
| 3 | 「低リスクの型」だけ、案を出すと同時に自動起動し、結果を `#consult` に報告 | 結果を見るだけ |

段3の低リスク条件（案）: 下書き PR で止まる作業（フローの磨き、ドキュメント、テスト付きの小さな実装）／回し先の週次使用量が上限内／お金・OTP・本番変更・外部送信を含まない／同時に走らせる数に上限。条件を外れたら段2に戻す。

おすすめは、まず段1を動かして実績を貯め、段2へ進み、型ごとに段3へ広げる順。段2・3は使用量の表と Supabase の履歴があって初めて安全に回せる。
