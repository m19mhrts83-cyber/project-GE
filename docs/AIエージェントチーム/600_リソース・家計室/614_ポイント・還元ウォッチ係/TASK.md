## 4. Requirements｜実装要件

### 4.1 起動・実行制御（工程1〜5・29・32）

- 既存の定時起動、朝の取りこぼし起動、手動起動を維持する。
- 全体停止スイッチを最優先する。停止中は手動取得と保留中の障害通知再送も実行しない。
- 既存の系統別停止機能を維持する。
- 停止時の短報は既存の通知経路を維持する。
- 手動実行は窓外・同日複数回を許容する。ただし停止・排他・サイト保護条件は解除しない。
- 成功済みの取得は繰り返さず、未完了部分だけ実行する。
- 正常スキップ・dry-runは本番成功に数えない。
- Vポイントは月印後も必要なcadence・PDCA等を継続する。
- 停止設定やstateの読取失敗で危険な再実行が生じないよう、安全側の処理を検討する。

### 4.2 テイチャン（工程6〜8・29・30）

- 既存のD4実装を優先して再利用する。
- 通常画面・メンテナンス・未ログインを区別する。
- メンテ中は原則3日間隔で確認する。
- 手動確認は間隔外でも可能とするが、排他制御を維持する。
- メンテ中は券数等の前回値を最新値として扱わない。
- 通常画面へ復帰したら通常の確認間隔へ戻す。
- 画面取得と抽選結果の成功を独立判定する。
- 抽選失敗時の自動再試行は最大1回とする。

抽選済みか不明な状態での再実行条件は未確定。二重抽選の可能性があるケースの自動化は保留する。

### 4.3 ETC還元（工程9）

- 既存の20〜26日の取得窓を維持する。
- 対象月の還元額であることを確認する。
- 未付与は「取得待ち」、技術障害は「失敗」と区別する。
- 取得待ちは窓内の翌日に再確認する。
- 26日の取得窓終了後も未取得なら#ops通知対象とする。
- 窓外の手動取得を許容する。
- 対象月が不明、または古い月のデータでは完了扱いにしない。
- 確定済みの過去履歴を誤って上書きしない。

### 4.4 Vポイント定例（工程10〜12・27）

- 既存の25日〜月末の窓Cを維持する。
- Tサイト履歴の基準日が対象月末以降であることを完全成功の条件とする。
- 古い履歴・基準日不明・監査フォールバックは部分成功とする。
- 履歴がない場合は失敗として区別する。
- 部分成功では月印を付けない。
- 利用可能な数値、基準日、取得元は表示する。
- 手動取得完了後は対象部分だけ再集計する。
- asks、PDCA板、last_routine_atの保存結果を確認する。
- Tサイトの手動取得日は固定しない。

D6の既存修正を再実装せず、テストと本番結果で確認する。

#### Olive

取得元ごとに以下を区別する。

- 部分成功
- 取得待ち
- 失敗
- 未確認

片方のカードだけ取得できた場合は、取得できたカードの達成率等を表示する。ただし、信頼できる両カードの情報が揃わない場合はカード間の寄せ先推奨を保留する。

取得失敗がexit 0に埋もれ、月印が誤って付く問題（F5・F9）を解消する。

#### 月印

- 取得・保存の成功と対象固有の完了条件を満たした場合だけ付与する。

- 未完了の取得元だけを再試行対象にする。
- Slack・ダッシュボードの失敗によって取得済みの月印を取り消さない。
- AMEX未接続だけを理由に既存Olive・Zaim定例全体を失敗させない。
- AMEXの公式照合状態は既存取得の完了状態と区別する。

### 4.6 保存・読み戻し検証（工程16・28）

- 既存stateを優先して利用する。
- 保存直後に読み戻し、対象月・取得結果・基準日・月印等を照合する。
- 保存・検証失敗時は取得済みデータを非公開領域に一時保持する。
- 外部サイトを再取得せず、保存だけ最大1回再試行する。
- 再試行後も不一致なら保存失敗とし、#ops通知対象とする。
- 保存未確認の結果を成功として下流へ渡さない。
- 月印の永続化と保存検証の整合性を保証する。
- 途中終了・競合・再起動で不正な完了状態が残らないことを検証する。

### 4.7 ダッシュボード反映（工程17・18）

- 保存済みstateからpushする。
- 年間特典も保存後の直接push対象とする。
- pushの戻り値だけで画面反映成功としない。
- 実際の表示データとstateを照合する。
- 不一致またはpush失敗の場合、保存済みstateから最大1回再pushする。
- 画面反映失敗は取得・保存成功と分離する。
- 人による画面確認は初回・変更時・障害時を中心とする。

### 4.8 Slack短報・障害通知（工程19〜21）

#### #report

- 既存の非公開控え保存を活用する。
- 投稿前に本文の控えを保存する。
- 投稿後に投稿結果を追記する。
- 控え保存失敗時は保存だけ最大1回再試行する。
- それでも失敗した場合は投稿を保留し、#ops通知対象とする。
- run ID等を用いて同一通知の重複を防止する。
- 投稿結果が不明な場合は既送信か確認する。
- 未送信が確認できた場合のみ最大1回再試行する。
- 送信済みか不明なまま再投稿しない。
- 投稿成功後の結果追記だけ失敗した場合は追記だけ再試行し、再投稿しない。
- dry-runの控えは実配信と明確に区別する。

#### #ops

- 障害が発生した工程・原因・次の対応を通知する。
- 通知失敗時は未通知情報を非公開側へ保存する。
- 全体停止がOFFの次回起動で保留通知を再試行する。
- 主保存先障害時は別系統の緊急ログを利用する。
- 障害通知の失敗で無限再帰や通知ループを発生させない。

#### 金額・秘密情報

D9を維持する。本人宛の既存Slack短報には実額を載せてよい。ただし公開リポジトリ・PR・テスト・公開資料には実額や秘密情報を記載しない。

### 4.9 人の判断・有効基準（工程22〜24）

判断ログに以下を記録する。

- decision ID
- 判断事項・AIからの提案
- 本人の選択（採用・見送り・保留）
- 本人が述べた理由の原文
- 対象・今回限り／次回基準
- 有効期限または期限なし
- 改定・取消の履歴
- 関連run ID・incident ID

理由がない場合は補作しない。

次回実行では明示採用された有効な基準だけを適用し、適用IDを記録する。

期限切れの場合は以下のとおり。

- 基準の適用を停止する。
- 過去の判断・旧基準は参考表示する。
- 「再判断待ち」を明示する。
- 取得済みの事実・数値は引き続き表示する。
- 期限切れ基準に依存する推奨だけを停止する。
- 以前の基準に自動復帰しない。

基準読取失敗時は該当する系統だけ安全側に停止・保留し、他の正常系統は継続する。

### 4.11 新規障害対応工程（33〜36）

#### 工程33：障害識別・履歴検索

- 工程＋障害分類＋エラーコードで同一障害を識別する。
- 過去の障害対応履歴を決定論的なルールで検索する。
- 事実、推定原因、本人判断を区別する。
- 実行時のAI呼び出しは禁止する。

#### 工程34：安全な自動復旧

- 事前承認された安全な対策だけを自動実行する。
- 過去の成功事例だけを実行許可の根拠にしない。
- 同一障害が連続3回発生したら該当する自動対策を停止する。
- 3回目の障害に対して停止対象の自動対策を実行しない。
- 他の正常系統は継続する。
- 自動復旧成功だけでは連続回数をリセットしない。
- 次回の該当工程の通常実行が成功した場合にリセットする。
- 正常スキップ、停止中、別系統の成功ではリセットしない。
- 個別処理の再試行上限と、複数runにまたがる連続発生回数を区別する。
- 未承認・安全条件外の場合は過去事例と対策候補を本人に提示する。

#### 工程35：障害対応履歴

- incident ID、run ID、関連decision IDを記録する。
- 発生事実、原因、対策、検証結果、再発回数を記録する。
- 失敗した対策も残す。
- 自動復旧の再開には原因・対策・検証結果の記録と本人の明示承認を必要とする。

#### 工程36：参照用ナレッジ生成

- 構造化ログを正本とする。
- 判断履歴・障害対応事例のMarkdownをプログラムで自動生成する。
- 正本とMarkdownを手作業で二重管理しない。
- 許可された人・AI社員のみ参照できるようにする。

### 4.12 D8：保存場所・保持期間・アクセス権

Mac上の既存非公開保存領域を優先する。実際の配置は既存環境を調査して決定する。

- incident-playbook.md：障害対応ナレッジ

保持方針：

| 対象 | 保持方針 |
|---|---|
| 詳細実行ログ | 180日 |
| 月次集約 | 3年 |

| 緊急ログ | 正本への反映・検証後に整理 |

保持期間経過だけでは自動削除しない。

アクセス権は最小限とし、バックアップは非公開・暗号化を原則とする。認証情報・APIキー・セッショントークンは記録しない。
