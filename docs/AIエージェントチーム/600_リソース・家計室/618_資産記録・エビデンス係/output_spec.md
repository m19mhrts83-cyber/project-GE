# 618 — トリガー・保存先・KURASHIFT反映の仕様

更新: 2026-11-14。ユーザー方針「数値履歴はDBに残ればよい。画像は最新の証拠を保存できるようにする」を反映。
状態: Phase 1–3を隔離worktreeで実装・ローカル検証済。本番DB/Storage/画面/通知は未変更。現行の適用手順と差分はphase3_report.md。

## 1. 今回の確定事項と保存先の選定

- 数値の履歴を記録の正本とする。実行のたびの画像保管は必須にしない。
- 画像は金融機関・名義・契約・画面種別ごとの最新の正常画面を1組持つ。毎月の画像アーカイブ・12か月分保管を基本運用から外す。
- 報告の出口はSlack。記録はDB、最新画像は非公開Storage、手順は社員フォルダと役割を分ける。
- 保存先の選定案: **財務と同じSupabaseプロジェクトの非公開Storage**。新設bucket名は `asset-evidence` 案。神大家QA用のSupabaseとは混在させない。
- 社員フォルダはGit・Drive同期対象のため、個人の残高画像を置かない。既存の同期・DB参照経路があるSupabaseへ寄せる方が、Macの起動状態に依存せず画面から確認しやすい。容量・既存のStorage設定は今回未調査で、追加料金なしを保証するものではない。
- 既存のOneDrive・debug画像は今回移動・削除しない。新しい画像を日付別に蓄積する方式へは進めない。

## 2. トリガーと実行範囲

### 通常の数値更新（既存を維持）

- Mac launchdは毎日09:10 JST、Mac起動時、朝の補完で起動。収集はISO週単位で判断する。
- 正常に記録済みの週は通常スキップ。未取得先の再試行条件・全入口の共通ロックは整備対象。
- KURASHIFTの手動ジョブも同じ受付に通す。GHAの日曜09:10設定はcloud-only補助で、銀行等のログイン取得の代替ではない。
- 数値だけ保存できた場合も数値更新は成功。撮影なしを失敗にしない。

### 最新画像の更新（必要時）

- 人が「最新の資産エビデンスを保存して」と依頼した時、対象の正常画面を取得する。
- 通常の数値取得で正常な画像が得られる場合は、その画像を最新へ置き換えることもできる。画像保管だけを目的とする定期的な再ログインは不要。
- 月次撮影ジョブの新設は基本案から外す。必要になった場合に別途日程を決める。

### 未完了分の取り直し（人の依頼）

- 02の入口: 松野さんが音声・チャットで「最新の資産証拠を取って」と声をかける。
- 03の入口: Slackの報告やKURASHIFTを確認し、うまくいかなかった対象について音声・チャットで「未取得分を取り直して」と依頼する。
- 指定runの未取得分だけを再取得し、成功済み対象は繰り返さない。取り直しが不要ならその実行は終了。
- **Slackは報告の出口のみ**。投稿・返信・✅リアクションをトリガーにする監視や承認後自動起動は本案から外す。317との起動連携も不要。
- 数値更新・画像更新・取り直し・KURASHIFT手動の全入口で共通ロックを使う。認証・銀行IB・OTPの担当境界は従来ルールを守る。

## 3. アウトプット1：数値履歴（既存を再利用）

- 保険・証券等: Supabase `portfolio_snapshots`。主要列は `account_id / as_of / value_jpy / cost_jpy / source / note`。
- 銀行等: Supabase `liquidity_snapshots`。主要列は `account_id / as_of / balance_jpy / source / note`。
- 既存はどちらも `account_id, as_of` が一意。別日の値は履歴に残り、同日・同口座の再取得は更新される。毎回の数値を追記する監査ログとは異なる。
- `as_of`は元データの基準日として扱い、取得日時と混同しない。取得日時、今回取得／既存値参照、対象別結果は実行結果メタデータとして補う。鮮度が不明な値を今回の値に見せない。
- 失敗した対象をゼロで上書きしない。最後の正常値とその基準日を残し、今回の失敗を別表示する。
- 保存後に対象件数・基準日を読み戻して確認する。画像の取得可否とDB保存結果は別々に扱う。
- 現行 `sync_meta.portfolio_weekly_at` は処理の完了時刻。`portfolio_weekly_summary` のlast_full_okだけで全対象が取得できたと判断しない。

## 4. アウトプット2：最新画像（新設案）

保存先の具体形:

`Supabase Storage / private bucket asset-evidence / 618/latest/{owner_uuid}/{scope}/{account_id}/{contract_key}/{view_key}.{a|b}.png`

- 口座ID・契約キーは内部ID。口座番号・氏名・金額をファイル名に入れない。名義別契約を混同しない。
- 契約全体を示すために複数画面が必要な場合、画面種別ごとに最新1枚。画像の日付別履歴を蓄積しない。
- 正常な画面・名義・契約・基準日を検証してからlatestを置き換える。失敗画像・ログイン画面・env転記メモは登録しない。
- 更新失敗時は前回の正常画像を保持する。画面には撮影日時、元データ基準日、今回更新に失敗した旨を出し、「最新取得済み」と誤表示しない。
- 画像メタデータ用 `asset_evidence_latest` を新設する案。キーは `account_id / contract_key / view_key`、保持項目は `storage_path / captured_at / source_as_of / sha256 / last_attempt_at / last_attempt_status / run_id`。銀行IDと資産IDの対応を確定してからスキーマ化する。
- Storage更新成功とメタデータ更新を照合し、途中失敗時は「更新確認待ち」とする。公開用の画像履歴を作らない。処理中の一時画像が残る場合の回収条件は実装時に定める。
- 最新画像の差し替えはこの方式の通常動作。既存のOneDrive・debug画像の一括削除や過去資料の整理とは別。
- bucketは非公開。閲覧は認証済みの所有者限定とし、サーバーで短時間の署名URLまたは認証付き配信を発行する。公開URL・Service Roleキー・署名URLをSlackや社員MDへ貼らない。
- 社員フォルダはこの仕様、手順、機密を含まない実行記録だけを保持する。

## 5. アウトプット3：KURASHIFTへの反映・確認

### 数値の反映先と確認先（本工程）

- 週次処理は `portfolio_snapshots / liquidity_snapshots / sync_meta` に保存する。
- KURASHIFTホームと `/portfolio` は同じDBを直接読む。資産の数値の反映・確認先は **KURASHIFT** とする。
- DB保存 → 保存件数・基準日の読戻し → KURASHIFT `/portfolio` 再読込 → 金額・基準日・対象別の未取得状況を保存結果と照合する。
- 既存 `/portfolio` は動的読込。新しいカードの有無やリアルタイム自動更新を、数値反映の完了条件にしない。
- DB保存だけ成功して画面照合が未済なら「数値DB保存済み・KURASHIFT反映未検証」と報告する。

### 最新証拠の閲覧（追加案）

- KURASHIFTに認証付き最新証拠画面を追加する案（パス案 `/portfolio/evidence`）。口座・名義・契約ごとの撮影日時・基準日・画像なし・前回分保持・更新確認待ちを表示する。
- 非公開Storageの画像を所有者が閲覧できるようにする。実装は未実施。

### JARVISの役割（補助の入口）

- 現状の `HomeKurashiftLink` はKURASHIFTへのリンク。JARVISは金額を反映する先ではなく、更新状況と閲覧先への入口とする。
- 追加する場合は「618 資産記録」状態カードに最終更新・未取得件数と、KURASHIFTの数値詳細／最新証拠画面へのリンクを出す。これは補助機能であり、KURASHIFTへの数値反映とは分けて管理する。
- JARVIS用に資産金額を二重転記しない。JARVISの補助カードが未実装でも、KURASHIFTでの反映確認は実施できる。

## 判断ログの記録・取得・適用（2026-11-14追加）

### フロー上の位置

実行受付・共通ロック → **判断ログと有効基準の取得** → 対象確定 → **人の判断が必要か確認** → 定型処理を実行 → 保存・KURASHIFT反映確認（適用基準と結果を関連付け）→ Slack報告 → 松野さんが結果確認・音声／チャットでフィードバック → **判断・理由をDBへ記録** → 今回の取り直しは03、採用した次回基準は次回開始時に取得する。

判断がなければ通常実行は終了。人の承認を毎回要求しない。判断が必要な対象のみ保留し、影響しない定型処理は進める。Slackは出口専用を維持する。

### 保存先と記録仕様

- 既存の共通DB `owner_decisions` を再利用する。`employee='618'`、`surface='asset_618'` を追加する案。現在の共通契約にはこのsurfaceがないため、契約・書込・読取の配線は未実装。既存APIがそのまま受付できると扱わない。
- 主要列: `decided_at / employee / surface / target_type / target_id / ai_proposal / final_text / note / action / payload`。run単位の案件IDと口座・契約の内部IDを対象に紐付ける。
- 記録内容: 判断事項、AI提案と理由、本人の選択、本人が述べた理由、対象、今回だけ／次回以降、適用開始・期限、関連run_id、元の依頼を照合できる参照、取消・改定元ID。
- 本人が理由を述べていなければ「理由未記入」。AIの推測を本人の理由として保存しない。金額・口座番号・画像・認証情報を判断ログ本文へ転記せず、必要な根拠はアクセス制御された内部IDで参照する。
- フィードバックはまず提案・コメントとして記録。`rule_accept`（本人が次回基準として明示採用）、`rule_once`（今回だけ）、`rule_reject`（採用しない）、`rule_revert`（過去基準の取消）等の既存actionを再利用する案。
- 決定・取消・修正は追記型。過去ログを上書きしない。同じ判断の再送は `payload.idem_key` で重複を防ぐ。保存成功と未保存を区別する。

### 取得するタイミングと条件

1. **毎回の実行前**: 定期・画像依頼・取り直しのどの入口でも、618の今回対象に関係するログをサーバー経由で取得する。
2. **判断を提案する前**: 同じ口座・契約・判断事項の過去の選択と理由を取得し、既存基準と新しい提案の差を示す。
3. **フィードバックを振り返る時**: 対象の判断ログと適用後の実行結果を取得し、同じ問題の再発や改善効果を確認する。本人がレビューを依頼した時・問題が再発した時に行い、新しい定期レビューを無断登録しない。

取得条件は `employee=618`、surface、対象の口座・契約・判断事項、適用開始・期限。必要範囲を取得し、ページング漏れや単なる最新N件切り捨てで有効基準を落とさない。取消・置換イベントを反映して有効な基準を組み立てる。既存の一覧・action名だけで自動採用しない。

### 適用と人の判断点

- 今回の明示指示を優先。採用済み・対象一致・有効期限内・未取消の基準だけを自動適用する。「今回だけ」は指定runとその明示された取り直しだけに限定し、翌週へ持ち越さない。
- 未判断・見送り・コメント・AI提案を次回基準へ昇格させない。以前の基準を覆す新指示が今回だけか恒久か不明なら、今回の対象に限定し恒久化しない。
- 判断点は、①対象追加／除外、②未取得の取り直し／見送り／手作業、③次回の判定・報告基準の変更。提案には「判断事項・おすすめ・理由・保留時の扱い」を付ける。
- 基準競合、対象・期限の不明確さは、影響する処理だけ止めて報告。取得失敗を「過去基準なし」と見なさない。既知の基準で安全に続行できない対象は保留する。
- 判断を受け取ったら保存を確認してからその判断の反映へ進む。記録失敗時は未保存と表示し、同じidem_keyで再保存する。次回基準を有効化した扱いにしない。無関係な正常数値の保存まで失敗にしない。
- runの実行記録へ `applied_decision_ids / applied_rule_version / run_id / target_ids / result_ref` を保存する案。判断ログとは別に「何を読んで適用したか」を追跡できるようにする。
- 実行後は、基準どおり動いたか・結果が改善したかを確認する。同じ失敗が続く場合も勝手に基準を書き換えず、改定案→本人の採用→新ログ→次回取得へ戻す。

### 受け入れ条件（未実装の検証項目）

- 「今回だけ」は次回に適用されず、採用済みの有効基準は次回に取得される。取消済み・期限切れ・見送り・別対象は適用されない。
- 取得したdecision_idと実際に使ったID、適用後の結果が照合できる。

- この更新は図・仕様の明文化まで。owner_decisionsへの実データ書込、共通契約の変更、実行workerへの接続、本番反映は未実施。

## Phase 3実装との対応（2026-11-14）

上記の「案／未実装」は設計時の記録。現在のローカル実装の正本はphase3_report.md。本番適用は未実施。
画像の物理パスへ所有者・scopeと2スロットを追加し、正常参照は一つ。更新失敗で前回正常画像を失わないための実装上の具体化で、画像履歴の蓄積ではない。asset_evidence_owners / asset_evidence_latest / asset_618_display_checksのSQLを準備。公開URL・署名URLではなく認証付きAPI配信を採用。
数値読戻しでは値・口座・記録日・取得元も照合し、元データ基準日は確認できない限り未確認。表示照合は新しい保存確認欄に対する照合で、既存配分集計全体の正しさを保証した扱いにしない。画像の名義・契約・元日付が未確認なら登録しない。Slack下書きは各結果を分け、実投稿しない。
