## 状態変更は提案が先（必須）

作業の結果として status を上げ／下げるとき（例: 定時が動いた→`運用確認`、意図OK→`運用`）:

1. **先にチャットで報告・提案**する（「〇〇なので `運用確認` に上げてよいですか？」）
2. 松野の了承後にだけ registry／マーカーを変える
3. 同一ターンで「運用確認に戻して」等と明示されたときだけ、提案省略して実行＋1行報告

**禁止**: 成果が出たからといって無言で `運用` や `運用確認` にする（315教訓 2026-10-11）。

**図確認の印 `flow_confirmed_at`**（2026-11-23 松野さん決定）：registry の任意項目。値は日付 `YYYY-MM-DD`。
- 松野さんが図を見て「これなら動く」と判断したあとに、各ブランチリーダー（300 ラスカル・600 ラコ・今後のリーダー）が入れる。日付は松野さんが判断した日。
- 根拠は項目に残した判断の記録。印を入れたら上の同期コマンドを実行する。印が無い間は、`設計中`→`運用確認` の提案は出ない（週次の段階レビュー）。

## 必須運用（了承後・作成時）

どのAIツール（Claude Code / Cursor / Codex / GenCode / Grok 経由の Jarvis 等）でも:

1. （提案了承済みで）`agents_registry.yaml` の `status` を直す（または新規行を足す）
2. 索引を必要なら直す
3. **必ず同期を実行**:

```bash
cd ~/git-repos && ~/selenium_env/venv/bin/python scripts/jarvis_agent_team_status_sync.py
```

これで: 社員マーカー ↔ 部門 `00_状態ボード.md` ↔ README接頭辞 ↔ Drive写し ↔ **Jarvisダッシュ `apps/jarvis-dashboard/data/agentTeam.json`** が揃う。

ダッシュ UI: https://jarvis-dashboard-amber.vercel.app/agent-team （本番反映は JSON の commit＋push）。  
作業フローの作り込みは Cursor インブラウザの FlowForge（ログイン **m19m**）。ダッシュは状況確認＋深リンクのみ（iframe 埋め込み不可）。

**組織図の正**は `agents_registry.yaml` → ダッシュ投影。ビルダー共有（`builder_source` / ATB）は編成の**参考リンク**（localStorage依存のため静的スナップショットにはしない）。  
**FlowForge 閲覧URL**は `config/flowforge_share_urls.json`（git追跡）を正。sync が `agentTeam.json` の `flowforge_share_url` に載せる（`.jarvis_state` だけだと別環境で消える）。

## 状態語と「魂がこもった」の関係

『魂がこもった』の定義は [`62_`](./62_ボット共通ルール入口_20261123.md)。3つ（磨き込み／図の確認と松野さんの判断／運用して回った）が揃うと `運用`。

| 揃ったもの | 状態 |
|---|---|
| なし | `候補` |
| 磨き込み中（図の確認前後） | `設計中` |
| 磨き込み＋図の確認＋松野さんの判断（運用を始めた） | `運用確認` |
| 3つ全部（回った） | `運用`＝魂がこもった |

上げる時の根拠（提案の中に書く。上げるのは松野さんの了承後）:

- `設計中`→`運用確認`：図の確認が済み、松野さんが「これなら動く」と判断し、運用を始めた。
- `運用確認`→`運用`：定時や実行が回った証拠（run・実行記録）があり、松野さんが意図OKと了承した。
- 定時でない社員は、定時の代わりに実際に使われて回った実行記録を証拠にする。
