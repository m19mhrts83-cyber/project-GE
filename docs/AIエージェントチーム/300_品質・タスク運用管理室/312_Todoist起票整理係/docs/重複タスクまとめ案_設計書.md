# 設計書：重複タスクまとめ案

- 業務：会話からのタスク候補選び（Slack・メール・会話から拾った候補を選び、重複や曖昧さを確かめてTodoistに登録します。）
- コンセプト：同じ用件に見えるSlack・メール・会話と既存のTodoistタスクから、AIが「既存タスクへ追記」「別タスクを作る」「登録しない」の3案を出します。依頼元・対象資料・完了条件を見比べて1案を選び、タイトル・期限・プロジェクト・追記文を必要に応じて直します。確定した内容をお題ごとに1件残し、Todoistへの反映は担当者が行います。

## ツールの中（AIの案を人が判断し、結果が残る）
- AIが出すもの：同じ用件かもしれない発言と既存のTodoistタスクをお題に、「既存タスクへ追記」「別タスクを作る」「登録しない」の3案を、違いが分かる説明付きで出します。最初は「Slackとメールの同じ依頼」「既存タスクへの催促」「似ている別案件」の3例で試します。
- 人が決めること：依頼元、対象の資料、完了条件を見比べて、3案から1つ選びます。既存タスクへ追記する場合は追記文を直せます。既存タスクを勝手に統合したり削除したりはしません。
- お題：発言と既存タスク（最初は例を3件入れておく。1つのお題に結果は1件）
- 判断の操作：比べて選ぶ（S05 比べて選ぶ（2〜4案を同じ大きさで並べて1つ選ぶ。「どれも違う」も置く。）　画面に出す言葉：既存タスクへ追記／別タスクを作る／登録しない　伝え方：理由タグを押す　学び方：選んだ群・選ばなかった群の共通項を基準案にする）
- 操作の流れ：AIが同じ用件への3案を並べる → 1案を選ぶか、どれも違うを選ぶ → タイトル・期限・追記文を直す → 決め手のタグを任意で押す → お題と確定内容が1件残る
- 決め手の選択肢：同じ資料／完了条件が別／もう済んだ／今やらない／タスクではない
- 残る結果：発言と既存タスク（例：佐藤のSlack・メール依頼／青葉社見積書を送付／11月12日／営業／未完了）／AIの3案（例：既存へ依頼経路を追記／同じ見積送付を新規作成／重複として登録しない、の各全文）／選んだ扱い（例：既存タスクへ追記）／確定した内容（例：対象：青葉社見積書を送付／期限：11月12日／営業／追記：佐藤さんからSlackとメールで同じ送付依頼を受領。）／修正前後（例：追記文の「11月12日までに青葉社へ送付する」を削除。既存の期限・タイトルと重なるため。）／本人が選んだ理由（例：同じ資料。未選択の場合は空欄で残します。）

### 最初に入れておく例（重複タスク整理案）
#### 例1
発言と既存タスク：
```text
Slackで佐藤「青葉社向け見積書を11月12日までに」。同日のメールでも同じ依頼。既存：青葉社見積書を送付／期限11月12日／営業／未完了。
```
1. 既存タスクへ追記：青葉社の見積依頼を集約
```text
対象：青葉社見積書を送付
期限：11月12日
プロジェクト：営業
追記文：佐藤さんからSlackとメールで同じ見積書の送付依頼を受領。11月12日までに青葉社へ送付する。
扱い：既存タスク1件を使い、新しいタスクは作成しません。
```
2. 別タスクを作る：メール依頼を独立して管理
```text
タイトル：青葉社向け見積書を送付する
期限：11月12日
プロジェクト：営業
説明：佐藤さんのメール依頼に対応し、青葉社向け見積書を送付する。
注意：既存の「青葉社見積書を送付」と同じ成果物のため、二重管理になります。
```
3. 登録しない：同じ依頼は既存タスクで対応
```text
登録対象：佐藤さんからの青葉社向け見積依頼
扱い：新規作成も既存タスクへの追記もしません。
理由：送付する資料と期限が既存タスクに含まれています。
継続するタスク：青葉社見積書を送付／11月12日／営業
```
#### 例2
発言と既存タスク：
```text
田中から「採用説明会の資料、どうなってますか？」。既存：説明会資料を田中へ送付／期限11月10日／採用／未完了。新しい資料や期限の指定なし。
```
1. 既存タスクへ追記：資料の催促を記録
```text
対象：説明会資料を田中へ送付
期限：11月10日
プロジェクト：採用
追記文：田中さんから進捗確認あり。資料の送付完了が求められており、新しい資料・期限の指定はなし。
扱い：既存タスクを使い、新しいタスクは作成しません。
```
2. 別タスクを作る：進捗への返答を管理
```text
タイトル：田中さんへ説明会資料の進捗を返信する
期限：設定なし
プロジェクト：採用
説明：説明会資料の進捗確認に返信する。資料送付は既存の「説明会資料を田中へ送付」で管理する。
完了条件：田中さんへ現時点の状況を伝える。
```
3. 登録しない：催促だけでは追加しない
```text
登録対象：田中さんからの説明会資料の進捗確認
扱い：新規作成も既存タスクへの追記もしません。
理由：新しい成果物や期限の指定がなく、資料送付は既存タスクで管理しています。
継続するタスク：説明会資料を田中へ送付／11月10日／採用
```
#### 例3
発言と既存タスク：
```text
鈴木との会話で「白波社向けにも導入資料を11月15日までに」。既存：青葉社向け導入資料を送付／期限11月13日／営業。白波社には別の料金表が必要。
```
1. 既存タスクへ追記：両社への送付を1件で管理
```text
対象：青葉社向け導入資料を送付
変更後タイトル：青葉社・白波社向け導入資料を送付
期限：11月13日
プロジェクト：営業
追記文：青葉社へ11月13日までに送付する。白波社には同社向け料金表を含め、11月15日までに送付する。
注意：既存期限は青葉社向けです。両社への送付で完了になります。
```
2. 別タスクを作る：白波社向けを分けて管理
```text
タイトル：白波社向け料金表を含む導入資料を送付する
期限：11月15日
プロジェクト：営業
説明：鈴木さんからの依頼。白波社向け料金表を含む導入資料を白波社へ送付する。青葉社向けの既存タスクは変更しない。
完了条件：白波社への資料送付が完了している。
```
3. 登録しない：白波社向けの依頼を見送る
```text
登録対象：鈴木さんからの白波社向け導入資料の送付依頼
扱い：新規作成も既存タスクへの追記もしません。
注意：既存タスクは青葉社向けです。白波社向け料金表の準備と11月15日までの送付は、Todoistに残りません。
```

### 業務の流れ
1. 【人】発言と既存タスクを選びます：Slack・メール・会話の発言と、同じ用件かもしれない既存タスクをまとめたお題を選びます。
2. 【AI】AIが3つの扱いを出します：追記先と追記文、新規タスクのタイトル・期限・プロジェクト、登録しない場合に残らない依頼を示します。
3. 【人】扱いを選び、内容を確定します：依頼元・対象資料・完了条件を見て1案を選びます。必要な項目を直し、理由タグは任意で押します。どれも使えない場合は、3案とも見送ったことを確定します。
4. 【人】確定内容を結果一覧に残します：お題・AIの3案・選んだ扱い・修正前後・理由を1件にまとめて保存します。同じお題を直した場合は、その1件を更新します。

## ツールの外（溜まった記録で案の作り方を直す）
- 記録が溜まる速さ：週に約10件の結果
- 選んだものの共通点（例）：送付先と完了条件を照合／追記は新しい情報だけ／別資料は別タスクで管理
- 選ばなかったものの共通点（例）：同じ依頼を経路別に起票／似た件名だけで一括管理／既存期限を根拠なく変更

### 記録を使うタイミング
1. その場｜今回の修正に使う｜今回の追記文を修正する：ツールの外で3件の結果をチャットのAIに渡し、まず今回使う文面だけを直してもらいます。1回の修正を今後すべての依頼に当てはめないよう指定します。（例：青葉社の結果を示し、「期限は既存タスクにあるので、今回の追記はSlackとメールで受領した事実だけにしてください」と頼みます。）
2. 〜10件｜参照例として渡す｜採用した扱いを参照する：10件ほどまでの結果から、似た依頼の採用内容と修正前後をチャットのAIへ渡し、次の案を作る際の参照例にしてもらいます。（例：同じ見積依頼が別経路で届いた例を添え、「新規作成ではなく既存タスクを使った例です。追記する必要があるかも分けて示してください」と頼みます。）
3. 〜30件｜共通点を分析して基準にする｜扱いの共通点を基準化する：30件ほどの結果をチャットのAIに渡し、選んだ案と選ばなかった案の共通点を抽出してもらいます。本人が確かめた基準だけを次の案作成の指示に書き足します。（例：「同じ資料でも送付先と料金表が違えば別タスク」という基準案を、白波社の採用結果などと照合して承認します。）
4. 〜100件｜チェックと並べ替えに使う｜候補の確認順を調整する：100件ほどの結果をチャットのAIへ渡し、案を作った後に送付先・資料・期限・完了条件の食い違いを自動で点検する指示を加えます。点検はツール外で行い、条件に合う案から並べてもらいます。（例：送付先が異なる場合は別タスク案を先にし、既存へ追記する案には「完了条件を広げます」と明記してもらいます。）
5. 結果が出たら｜成果で基準を見直す｜実務の結果で基準を見直す：担当者が後日確認した二重起票・未処理の依頼・不要な追記をチャットのAIへ渡し、関連する基準を修正または取り消してもらいます。（例：進捗確認を登録しなかった後に返信を忘れた例を示し、「催促はすべて登録しない」を取り消し、資料送付と返信の完了条件を分ける基準に改めます。）

### 基準の例
- 送付先・資料・完了条件が同じなら、新規作成を第一候補にしません。新しい情報があるときだけ既存への追記を勧めます。（範囲：同じ依頼がSlackとメールなど別経路で届いた場合／根拠：青葉社の見積依頼では既存への追記が選ばれ、同じ見積送付の新規作成は選ばれなかった結果などを確認します。）
- 送付先や必要資料が違う場合は、文面が似ていても別タスク案を先に出します。（範囲：顧客別の見積書・導入資料など、送付ごとに完了を確認する仕事／根拠：白波社向け料金表を含む資料送付を、青葉社向けとは分けた結果などを確認します。）
- 進捗確認では、元の作業と返信を分けて示し、催促だけを理由に元の期限を変更しません。（範囲：「どうなってますか？」など、新しい期限が示されていない発言／根拠：説明会資料の進捗確認で、資料送付の期限を保ったまま返信だけを別タスクにした結果などを確認します。）

### 効いているかの確かめ方
- ツール外で、似た依頼について指示を直す前後の案を比べ、担当者が重複起票を避けられる扱いを選べたか、タイトル・期限・追記文の修正が何だったかを確認します。
- 週ごとに新規作成案と既存タスクを照合し、同じ送付先・資料・完了条件のタスクを二重に作ろうとした例が残っていないか確認します。
- 週ごとに元のSlack・メール・会話記録から一部を見直し、候補に出なかった依頼と、登録しなかったため未処理になった依頼を別々に数えます。判断結果だけで拾い漏れが減ったとは判断しません。

## 注意点
- 既存タスクの統合・削除・期限変更は勝手に行いません。結果の保存はTodoistへの反映完了を意味しないため、担当者が反映先と内容を確認します。
- チャットのAIへ渡すときは、顧客名・会話の個人情報・未公開の金額などを必要に応じて置き換え、タスクの状態も確認時点を明らかにします。
- 元の発言・AIの案・本人の確定内容を生の結果として残し、ツール外で作るAIの理由仮説と再利用基準は別に管理します。理由未選択を同意とせず、「今やらない」や「もう済んだ」を恒久的な除外条件にしません。
- 選ばなかった＝嫌い、ではない。候補の違いが多すぎると理由を一つに絞れない。
- 文面が似ているかよりも、送付先・資料・完了条件が同じかを比べ、追記のために既存タスクの対象や期限を広げる案は特に確認します。

## 設計の原則
- 理由を毎回書かせない。自然な操作から対象・差分・結果を取り、価値が高い場面だけ追加で聞く。
- 「今回だけ」と「次も同じに」を分ける。一度の修正を全部に広げない。
- 本人の理由と、AIが推測した理由を分けて保存する。未確認は仮説のまま。
- 記録が増えたこと＝精度が上がった、と表示しない。「記録した／次に参照した／出力が変わった／成果が良くなった」を段階で分ける。
- 生ログ・AIの解釈・再利用ルールを別に持ち、解釈が誤っていても元の判断に戻れるようにする。

業務の元の説明：Slack・メール・会話のやり取りから「やりたい」「どうなってますか？」などのタスクの種をAIが拾い、Todoistに起票する／しないの案をSlackカードで出す。私はカードで「する」「しない」を押し、しないときは理由を一言（重複・もう済んだ・今やらない・タスクではない）付ける。起票するときはタイトル・期限・プロジェクトを直すことがある。週に10件程度あり、拾いすぎと拾い漏れを減らしたい。
