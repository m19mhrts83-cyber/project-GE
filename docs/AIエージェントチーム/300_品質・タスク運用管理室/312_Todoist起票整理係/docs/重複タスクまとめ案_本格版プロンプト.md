これから「重複タスクまとめ案」というツールを作り、使う人と一緒に育ててください。「会話からのタスク候補選び」（Slack・メール・会話から拾った候補を選び、重複や曖昧さを確かめてTodoistに登録します。）の担当者が、今日の仕事で使うものです。

次の4段階を順に進めます。1つ終わるたびに、使う人の返事を待ってください。
1. ツールを作る：AIの重複タスク整理案を人が選ぶ・直す・見送ると、結果が残るツール。最初は例を3つ入れておき、新しいお題にはサーバーのAIが案を出す
2. 使ってもらう：3つの例で判断してもらい、記録をチャットに貼ってもらう
3. 記録で案の作り方を直す：データ、分析結果、直す前と後の順に説明し、案を作り直してツールに入れ直す
4. 実際のアウトプットを作る：直した作り方で、今日の仕事を仕上げる

第1段階はツールの中の話、第3段階はツールの外の話です。ツールそのものに、記録から案の作り方を直す機能は入れません。
使う人は途中でいつでも質問できます。質問には、段階を進めずに短く答えてください。使う人は開発者ではないので、専門用語を使わずに説明してください。

## 進め方の約束（使う人は初心者です。一緒に作ります）
- 伴走する：1歩ずつ進める。1つ終わるたびに「できたこと」と「次にやること」を1〜2行で伝える
- 段階的に作る：まず動く最小のものを作り、試してもらってから足す。一度に大きく作らない
- すぐ試せるようにする：最短で動く完成品を先に出す。飾りや凝った機能は後回しにする
- まず手元のパソコンだけで動かす。公開（デプロイ）は必須にしない。使う人が公開したいと言ったときだけ、Vercel を提案し、使う人の環境（GitHub のアカウント、入っているツールなど）を聞いて、それに合わせた手順を案内する
- 手順・やり方は別ファイルに書く：起動や公開の手順は SETUP.md に、番号付きで丁寧に書く。チャットには要点だけ書き、「SETUP.md の手順2を見てください」のように案内する
- 説明は端的に、簡単に：1回の返事は短く、専門用語を避ける。使うときは一言で言い換える
- 環境を汚さない：Python を使うなら uv（uv init / uv add / uv run）で、プロジェクトの中に仮想環境（.venv）を作る。Node なら package.json に入れ、-g のグローバルインストールはしない。パソコン全体の設定は変えない。どうしても必要なら、理由を伝えて許可をもらう
- 足りないものは説明する：必要なツール・コネクタ・機能（APIキー、GitHub、Vercel、データベースなど）が使えないときは、黙って飛ばさず、何が足りないか、なぜ要るか、どう用意するかを短く伝える。無くても進められるとき（例の3件で試す、など）は、先に進める。キーの値はチャットに書かせない

# 第1段階：ツールを作る（ツールの中の話）
手元のパソコンで動くWebアプリとして作ります。最初に、作る画面と使う技術を3行で伝え、確認を待たずに作り始めてください。技術は任せます。迷ったら、依存が少なくすぐ動く方を選びます。

## 画面
上から順に、次の3つだけを1画面に置きます。
1. お題：入力欄1つ「発言と既存タスク」（複数行）と「案を出す」ボタン。その下に、お題を切り替える小さなボタン（例1・例2・例3、新しいお題は続けて増える）。決めたお題には印を付ける。開いた時点で例1を表示する
2. 案：いまのお題に対するAIの重複タスク整理案を並べる。例の3件は最初から入っているので、開いた瞬間に判断できる
3. 結果：決めたものの一覧と「記録をコピー」ボタン。一覧は1件1行で、開くとできあがりの全文を読めて、そのままコピーできる

### 案の判断
- 重複タスク整理案を3つ、同じ大きさのカードに本文ごと並べる
- カードごとに「これを使う」と「直して使う」を置く
- 「直して使う」を押すと、そのカードの本文がその場で文章欄になる。直して「これで決める」を押すと、カードには直した本文を出す
- カードの下に「どれも違う」を1つ置く
- 決めると、そのカードに「決定」の印が付き、ほかのカードは薄くなる
- 決めた場所のすぐ下に、「決め手」の小さなボタン（同じ資料／完了条件が別／もう済んだ／今やらない／タスクではない）を出す。押さなくても進める
- 決めた場所のすぐ下に「次の例へ」を出す。決めた直後に、そこが見える位置まで画面を動かす
- 1つの例に結果は1件だけ。同じ例で決め直したら、前の結果を上書きする

### 案の作り方（最初の版）
AIの案はこの作り方で作ります。下の例も、この作り方で作ったものです。
```text
「会話からのタスク候補選び」の担当者を手伝います。同じ用件かもしれない発言と既存のTodoistタスクをお題に、「既存タスクへ追記」「別タスクを作る」「登録しない」の3案を、違いが分かる説明付きで出します。最初は「Slackとメールの同じ依頼」「既存タスクへの催促」「似ている別案件」の3例で試します。
1つのお題について、切り口の違う重複タスク整理案を3つ作ります。
案は、見出しと本文だけにします。前置きや説明は書きません。

【基準と良い例：最初は空。第3段階で書き足す】
```

### 最初に入れておく例
この業務で実際に使う形のまま、画面に入れておきます。
#### 例1
発言と既存タスク：
```text
Slackで佐藤「青葉社向け見積書を11月12日までに」。同日のメールでも同じ依頼。既存：青葉社見積書を送付／期限11月12日／営業／未完了。
```
1. 既存タスクへ追記：青葉社の見積依頼を集約
```text
対象：青葉社見積書を送付
期限：11月12日
プロジェクト：営業
追記文：佐藤さんからSlackとメールで同じ見積書の送付依頼を受領。11月12日までに青葉社へ送付する。
扱い：既存タスク1件を使い、新しいタスクは作成しません。
```
2. 別タスクを作る：メール依頼を独立して管理
```text
タイトル：青葉社向け見積書を送付する
期限：11月12日
プロジェクト：営業
説明：佐藤さんのメール依頼に対応し、青葉社向け見積書を送付する。
注意：既存の「青葉社見積書を送付」と同じ成果物のため、二重管理になります。
```
3. 登録しない：同じ依頼は既存タスクで対応
```text
登録対象：佐藤さんからの青葉社向け見積依頼
扱い：新規作成も既存タスクへの追記もしません。
理由：送付する資料と期限が既存タスクに含まれています。
継続するタスク：青葉社見積書を送付／11月12日／営業
```
#### 例2
発言と既存タスク：
```text
田中から「採用説明会の資料、どうなってますか？」。既存：説明会資料を田中へ送付／期限11月10日／採用／未完了。新しい資料や期限の指定なし。
```
1. 既存タスクへ追記：資料の催促を記録
```text
対象：説明会資料を田中へ送付
期限：11月10日
プロジェクト：採用
追記文：田中さんから進捗確認あり。資料の送付完了が求められており、新しい資料・期限の指定はなし。
扱い：既存タスクを使い、新しいタスクは作成しません。
```
2. 別タスクを作る：進捗への返答を管理
```text
タイトル：田中さんへ説明会資料の進捗を返信する
期限：設定なし
プロジェクト：採用
説明：説明会資料の進捗確認に返信する。資料送付は既存の「説明会資料を田中へ送付」で管理する。
完了条件：田中さんへ現時点の状況を伝える。
```
3. 登録しない：催促だけでは追加しない
```text
登録対象：田中さんからの説明会資料の進捗確認
扱い：新規作成も既存タスクへの追記もしません。
理由：新しい成果物や期限の指定がなく、資料送付は既存タスクで管理しています。
継続するタスク：説明会資料を田中へ送付／11月10日／採用
```
#### 例3
発言と既存タスク：
```text
鈴木との会話で「白波社向けにも導入資料を11月15日までに」。既存：青葉社向け導入資料を送付／期限11月13日／営業。白波社には別の料金表が必要。
```
1. 既存タスクへ追記：両社への送付を1件で管理
```text
対象：青葉社向け導入資料を送付
変更後タイトル：青葉社・白波社向け導入資料を送付
期限：11月13日
プロジェクト：営業
追記文：青葉社へ11月13日までに送付する。白波社には同社向け料金表を含め、11月15日までに送付する。
注意：既存期限は青葉社向けです。両社への送付で完了になります。
```
2. 別タスクを作る：白波社向けを分けて管理
```text
タイトル：白波社向け料金表を含む導入資料を送付する
期限：11月15日
プロジェクト：営業
説明：鈴木さんからの依頼。白波社向け料金表を含む導入資料を白波社へ送付する。青葉社向けの既存タスクは変更しない。
完了条件：白波社への資料送付が完了している。
```
3. 登録しない：白波社向けの依頼を見送る
```text
登録対象：鈴木さんからの白波社向け導入資料の送付依頼
扱い：新規作成も既存タスクへの追記もしません。
注意：既存タスクは青葉社向けです。白波社向け料金表の準備と11月15日までの送付は、Todoistに残りません。
```

### 「案を出す」の動き
- 押すだけでサーバー側のAIが重複タスク整理案を出す。新しいお題が切り替えボタンに増える。待っている間は進み具合を見せる
- APIキーは環境変数に置き、画面には出さない。キーが無いときも、例の3件は最後まで試せる
- 案の作り方は prompts/proposal.md の1ファイルに置き、コードに直接書かない。呼び出しは1か所にまとめる

### 結果の残し方
- 決めた時点で自動で残す。使う人が項目を埋める場面は作らない
- 残すもの：論点（発言と既存タスク）、AI候補すべて、判断（どの案をどうしたか）、できあがり、選んだ理由（押した決め手）
- データベースに残す（最初は SQLite でよい）。サーバーを再起動しても消えない。どの版の作り方で出した案かも裏で残す
- 「記録をコピー」は次の形のJSONをコピーする。全部の例を1つの配列に入れる。項目名は日本語のまま、{ } の部分に実際の内容を入れる
- JSON.stringify で作り、本文に改行や引用符があっても壊れないようにする。決めていない例は入れない
- プレビューの中ではコピーが禁止されていることがある。navigator.clipboard が失敗したら、隠した文章欄と document.execCommand("copy") でコピーする。それも失敗したら、全文を選択した文章欄を画面に出し、「この内容をコピーしてチャットに貼ってください」と書く。黙って失敗しない。コピーできたら「コピーしました」と出す
- 「どれも違う」を選んだ例は、判断を「どれも違う」、できあがりを空にする
```json
[
  {
    "例": "例1",
    "論点": "{お題}",
    "AI候補": [
      {
        "案": "案1",
        "見出し": "{見出し}",
        "本文": "{本文}"
      },
      {
        "案": "案2",
        "見出し": "{見出し}",
        "本文": "{本文}"
      },
      {
        "案": "案3",
        "見出し": "{見出し}",
        "本文": "{本文}"
      }
    ],
    "判断": "案2を直して使った",
    "できあがり": "{決めた本文}",
    "選んだ理由": "{押した決め手。押さなければ空}"
  }
]
```

## ツールに入れないもの（いちばん大事）
- 入力欄を増やすこと。入力は「発言と既存タスク」の1つだけ
- 記録を分析する機能、学習する機能、過去の結果を次の案に自動で入れる機能。ツールは結果を残すだけにする。直すのは第3段階でチャットの側が行う
- 手順の説明、番号付きのステップ、設定の画面、保存ボタン
- 画面に見えるJSON、コード、内部のID、英語の項目名、版番号、「ループ」「ログ」「学習」「精度」のような言葉。JSONになるのは「記録をコピー」でコピーされる中身だけ

## 作り終える前に確かめること
- 例を選ぶ・直す → 結果が残る、新しいお題で案を出す、決め直すと結果が上書きされる、を自動テストで確かめる
- サーバーを再起動しても、結果が消えていない
- 起動の方法を、使う人がコピーして貼れる形で1つだけ書く。詳しい手順（準備・起動・困ったとき・公開したいとき）は SETUP.md にまとめる

# 第2段階：使ってもらう
ツールを起動したら、開くアドレスを伝え、次の案内をそのままチャットに書いて止まります。
> 「重複タスクまとめ案」ができました。入っている3つの例で、案を選ぶ・直す・見送るを試してください。押すだけで結果が残ります。
> 3つ終わったら、画面の「記録をコピー」を押してこのチャットに貼るか、「使いました」とだけ書いてください。
> 記録から分かったこと、案の作り方をどう直したか、案がどう変わったかを、順にお見せします。分からないことがあれば、このチャットでいつでも聞いてください。

# 第3段階：記録で案の作り方を直す（ツールの外の話）
「使いました」と書かれたら、データベースの記録を自分で読みます。貼られたときは貼られた内容を使います。
記録を受け取ったら、次の順に進めます。
1. 読み取る：記録の論点・AI候補・判断・できあがり・選んだ理由から、選ばれた案と選ばれなかった案の違い、人が直した箇所、「どれも違う」や見送りになったものの共通点を見る
2. 直す：prompts/proposal.md を書き換える。複数の例で繰り返された判断を基準として書き足し、良かったできあがりを見本として最大3件入れる。1件だけの判断は基準にせず、候補として説明に書く
3. 作り直す：新しい作り方で、同じ3つのお題の案をAIに出し直し、直す前の案と見比べる。新しい案には新しい結果が付く。前の案と結果は消さない
4. 変えないもの：画面の構成、ボタン、記録の残し方。分析や学習の機能をツールに足さない
5. 説明を書く。変更の内容と日付は improvements.md に残す

### 説明の形
使う人が知りたいのは、データから何が分かり、何をどう直したかです。必ず次の順で書きます。
```text
## 1. データ：受け取った記録（例○件、判断○件）
- 内訳：{採用○件、直して採用○件、見送り○件 など}
- 注目した記録：{例の番号と論点}｜{AI候補の見出し} → {判断}｜{人が直した箇所、または選んだ理由}　※3件まで

## 2. 分析結果：データから分かったこと
- {分かったこと}（{何件中何件か}。根拠：{例の番号と記録}）　※3つまで
- まだ基準にしないこと：{1件だけの判断}

## 3. Before / After：何をどう直したか
直した場所：{案の作り方のどの部分か}
直す前：{変えた部分の前の文}
直した後：{変えた部分の後の文}
直した理由：{2の分析結果のどれを受けたか}

## 4. Before / After：案がどう変わったか（同じお題で比べる）
例1
直す前の案：{前の案}
直した後の案：{新しい作り方で作った案}
効いた基準：{どの基準で変わったか}

## まだ分からないこと
- 件数が少なくて言い切れないこと
```
- 直すのはほとんどの場合、案の作り方（案を作るときの指示文）です。3の「直す前」「直した後」は、案の作り方の文をそのまま引用し、要約しません。案の作り方以外も直したときは、同じ形で続けます
- 2の分析結果は、3の直した理由と必ずつなげます。データに無いことを分析結果に書きません
- 選んだ理由が空の記録は、判断と直した箇所から読み取り、推測は「〜と見られます」と書きます
- JSONや項目名をそのまま見せず、普通の言葉で書きます
- 数字で精度を約束しない。記録が3件でも、言えることだけを言う
- 使う人が「違う」と言った基準は外す

# 第4段階：実際のアウトプットを作る
ツールを直したら、次の内容をチャットに書いて止まります。
> 案の作り方が直りました。今日の実際のお題を入力欄に入れて「案を出す」を押してください。選んで直せば、できあがりはそのまま仕事に使えます。
> 使って記録が溜まったら、また「使いました」と書いてください。何度でも直せます。

使う人に頼まれたら、チャットでも手伝います。できあがるまで相談に乗ります。

# 効いているかの確かめ方
- ツール外で、似た依頼について指示を直す前後の案を比べ、担当者が重複起票を避けられる扱いを選べたか、タイトル・期限・追記文の修正が何だったかを確認します。
- 週ごとに新規作成案と既存タスクを照合し、同じ送付先・資料・完了条件のタスクを二重に作ろうとした例が残っていないか確認します。
- 週ごとに元のSlack・メール・会話記録から一部を見直し、候補に出なかった依頼と、登録しなかったため未処理になった依頼を別々に数えます。判断結果だけで拾い漏れが減ったとは判断しません。
