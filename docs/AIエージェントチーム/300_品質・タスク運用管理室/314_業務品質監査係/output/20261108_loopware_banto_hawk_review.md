# Loopware共有案 — 番頭さん・ホーク向け（2026-11-08）

## 目的

LoopwareをTodoistの新しい起票・完了本線にせず、312／313の判断を記録し、314が改善材料として振り返る仕組みとして共有する。

## 確認したこと

- 公開画面 `/` はハブ、`/312` は起票の扱いと拾い漏れ、`/313` は完了候補と閉じ漏れの判断画面。
- 312は「既存へ追記／別作成／登録しない」、313は「済んだ／いつ・優先／やめる」を記録する。自動学習はせず、判断を集計して人がプロンプト・検知処理へ反映する設計。
- UIはブラウザ内 `localStorage` に保存し、サーバー設定時はAPI経由でも保存する。API保存失敗時も画面側の記録は残るため、画面表示だけでは共有DBへの保存確認にならない。
- 312のDB先は `task_loop_*`、313は既存 `owner_decisions`。314の週次運用は `owner_decisions` を読む想定なので、312ログの週次集計接続を確認・整備する必要がある。
- 313画面は現状、選択内容の記録が中心。画面の選択がTodoistのコメント・完了・期日変更を実行したとは限らない。Todoist処置の本線は既存の313 Slack／CLI運用。
- 2026-11-07の314草案には `owner_decisions` 読み取り失敗（migration未適用の可能性）が記録されている。現在のDB適用状態は未確認。

## 役割分担案

- **番頭さん**: 巡回で停滞・忘れ物・準備不足を発見し、根拠・既存対応・次回確認日を添えて追跡。Loopware／Todoistに既存対応があれば重ねて起票しない。
- **ホーク**: 攻めの横断整理、目標・優先順位・担当の提案。番頭さんの指摘と既存対応を見て、週次統括で重要なものを束ねる。日常巡回を重複して行わない。
- **312／313**: Todoist候補提示・承認・実処置の既存本線を維持。Loopwareは判断の記録・再評価に使う。
- **314**: 312／313の判断ログを週次で振り返り、繰り返し修正される型をプロンプト／検知処理の改善案にする。
- **松野**: 優先順位、承認、最終判断。

## 4つの合図への当てはめ

| 合図 | 活用案 |
|---|---|
| 人が頼む | `/todoist`・`/todoist-batch`等から判断画面を開く。実処置は既存承認ルールに従う |
| 時間 | 既存312取りこぼし確認・313 20時ダイジェストを候補提示に使う。314は週次集計 |
| イベント | 新着材料・Slack候補・完了相当の証拠を既存レーンへ渡し、IDで重複照合してから判断 |
| 見回り | API失敗・重複・停滞・番頭指摘の未解決を確認。低信頼や異常は人に残す |

## 改善提案

1. Loopwareの312／313ログが314週次レビューで読めるようにする。どちらのDB表を使うかに関わらず、集計経路と保存成否を明示する。
2. 候補ID／Todoist task IDを判断ログに通し、同じ候補の再判断で重複行・重複起票を増やさない。
3. 「判断を記録した」と「Todoistを実際に更新した」を別状態として表示・集計する。Todoist APIによる処置自動化は今回の設計に含めない。
4. ログを314が確認し、同じ修正が複数回あった場合に人手でプロンプト／検知ルールを更新する。高信頼型の自動化は誤判定を評価できるデータができてから段階導入する。

## コーディング引継ぎの範囲

実装担当向けの `TASK.md` を同じフォルダに置いた。対象はログ保存・314集計接続・画面の状態表現と重複防止。外部送信、Todoistの完了・期日変更・削除、デプロイは含まない。
