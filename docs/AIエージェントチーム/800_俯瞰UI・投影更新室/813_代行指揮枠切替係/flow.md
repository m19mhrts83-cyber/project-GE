## 2. コメント（気づいた点）

1. **前提が古くなっている**。10/25 の4者運用（[`50_`](../../50_4者共通運用と品質改善_20261025.md)）で「社員ごとにツールを固定しない。利用枠・タイミング・作業内容で松野さんが実行者を選ぶ」に変わった。Claude Pro も 10/26 に継続が決まった。「枠が切れたら決まった順に切り替える」という 813 の型は、もう本線ではない。
2. **いま本当に要るのは「切替」より「配車」**。松野さんの狙いは「現行コードをフライデーに渡すルーティンで役割分担し、使用量を分散する」こと。枠が切れてから動くのではなく、**作業を出すときに誰に回すかを提案する**係にする方が、ゴールに直結する。

4. **611 との境目があいまい**。611 も「使用状況の把握＋頻度の減増」を持っている。611＝材料を集める係（週次の使用量表）、813＝その表を見て作業の回し先を決める係、と分けると重複しない。

## 3. 思い描くフロー（案）

型: 開始トリガー → 経路 → 合流 → 点検 → Slack

| 段 | 内容 | 担当 |
|---|---|---|
| トリガーA（人が頼む） | Slack や Todoist で「これ誰にやらせる？」「フライデーに回して」 | 松野 |
| トリガーB（届いたら） | Todoist に `要Jarvis連携` 等の実装タスクが起票されたとき（例: 814・815 の実装切り出し） | ルール |
| トリガーC（見回り） | 週次（日曜、611 の週次に相乗り）。Cursor の使用量が警告域（既存の閾値 70%）に入ったら臨時でも | ルール |
| 経路1（材料） | 611 の使用量表を読む（Cursor 手入力％、Claude Code・Codex のローカル集計、GenCode 手入力） | ルール |
| 経路2（作業） | 回したい作業を読む（Todoist の対象タスク、社員フォルダの `TASK.md` `status: queued`） | ルール |
| 合流・判断 | 作業の種類 × 残り枠で回し先を決める。目安: 読む・設計＝ミスレモン、実装＝フライデー、レビュー・お金まわり＝ジャービス、どれかが逼迫＝チャッピー代行 | AI（軽量） |
| 引き継ぎ | 回し先が決まった作業は `TASK.md` に executor・完了条件・読むファイル・次の一手を書いた「渡し票」を作る | AI（軽量） |
| 点検・報告 | `#consult` に「この作業を誰に、理由、渡し票のリンク」＋「次の担当」3行。松野さんが OK したら回す。週次は `#ops` に配車の実績1通 | 松野承認 |

**4点まとめ**

- トリガー: 人が頼む＋実装タスクの起票＋週次見回り（Cursor 警告域で臨時）
- 権限: 読む＝使用量・Todoist・`TASK.md`／書く＝`TASK.md` の渡し票だけ。ツールの切替・課金変更・社員の停止はしない
- 作業内容: 作業の回し先の提案と、渡し票づくり
- 報告: 回し先の提案は `#consult`（承認待ち）、週次の実績は `#ops`

AI は「回し先の判断」と「渡し票の文面」にだけ使う。軽いモデルで足りる量なので、使用量を分散させるための係そのものが重くならないようにする。
