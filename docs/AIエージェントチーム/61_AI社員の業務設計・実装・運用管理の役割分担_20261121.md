- 関連: [`54b_`](./54b_FlowForge読取プロキシ_OpenAPI_20261106.md)（FlowForge の読み書きの仕組み・置き場の決まり）、

## 1. 役割

| 対象 | 役割 |
|---|---|
| FlowForge | AI 社員の業務フローを可視化・設計する（業務設計図） |
| Jarvis ダッシュボード | エージェントチームの稼働・実績・状態を確認する（運用管理） |
| ChatGPT（チャッピー） | 業務の整理、FlowForge の設計、設計レビュー、実装要件・受け入れ条件の検討 |
| ラス隊長（300 の隊長） | 300番台の業務の棚卸し、優先順位、実装の進行管理 |
| Claude Code（Miss Lemon） | 実装・テスト・セルフレビュー・修正 |

**設計情報と運用実績を、無理に FlowForge へ集めない。**

## 2. 流れ

| # | 担当 | 内容 |
|---|---|---|
| 1 | ラス隊長 | 300番台の棚卸し・候補の提案 |
| 2 | ChatGPT × FlowForge | 業務設計（起動条件・処理・判断・通知・人の承認） |
| 3 | Claude Code | 実装・検証（コード・テスト・修正を1つの実装スレッドで終える） |
| 4 | Jarvis ダッシュボード | 運用状況の可視化（稼働・成功失敗・実績） |
| 5 | 改善 | 業務上の変更は FlowForge へ、実装の変更は Claude Code へ |

- 候補は松野さんが選ぶ。選ぶまで、実装と既存フローの変更は始めない
- 新しい AI 社員は、原則として業務フローを設計してから実装する
- 既存のプログラムがある場合は、その実装を踏まえて業務の流れを整理すればよい

## 3. FlowForge に書くこと・書かないこと

- 書く: 起動条件・処理・判断・通知・人の承認。業務の流れが直感的に分かることを最優先にする
- 書かない: コードのファイル名・関数名（必要な場合だけ）、日々の運用実績、コードとの詳細な対応表
- 実績管理の機能を FlowForge に足さない。運用実績は Jarvis ダッシュボードのエージェントチームを基本にする
- FlowForge を直しただけで「実装も変えた」とは扱わない

## 4. FlowForge の制約と編集の決まり

| 決まり | 内容 |
|---|---|
| 矢印 | 1ノードにつき入り1本・出1本まで（FlowForge の仕様） |
| 合流・分岐 | 主な流れを矢印で表し、例外・分岐は説明文で補う。制約を無理に崩さない |
| 既存フローの変更 | 説明文・タイトル・接続の変更は `patch_flowforge_flow` を優先する |
| ノードの追加・削除 | この時だけ `queue_flowforge_edit` を使う |
| 承認 | FlowForge の変更は、松野さんの明示の了承の後に行う |
| 確認 | 変更の後、`verified=true` を確かめる |

仕組みと原因の詳細は [`54b_`](./54b_FlowForge読取プロキシ_OpenAPI_20261106.md)。
ChatGPT から編集できるのは、置き場（Chrome の既定プロフィール）へ移したフローだけ。**2026-11-21 時点で移してあるのは 311 のみ。**
次の社員の設計に入る前に、その社員のフローを置き場へ移す（手順は 54b「置き場の決まり」）。

## 5. 実装の手順（Claude Code）

1. `AGENTS.md`・既存コード・テスト・Git の変更状況を確かめる
2. ChatGPT で確定した業務仕様と FlowForge の設計を確かめる
3. 簡潔な実装計画を作る
4. 必要最小限の変更を実装する
5. テスト・セルフレビュー・修正・再検証を、同じスレッドで終える
6. 変更内容・テスト結果・残っている課題を報告する
7. 運用実績を、Jarvis ダッシュボードの既存機能で扱えるか確かめる

- 既存の管理機能・ログの仕組みを優先して使い回す。不要な新規開発は避ける
- 削除・対外送信・契約・有料操作・デプロイは、事前の了承が要る
- 既存の未コミットの変更を守る。秘密を出力しない
- 案件ごとの実装要件は、案件ごとの `TASK.md` で渡される

## 6. 311 で得た知見

- 既存の FlowForge を2回直した。実運用に合わせて、説明を「AI の3点判定」から「Python による4項目判定」に統一。
  起動経路 A・B、OK／NG の通知、人による承認との境界を明確にした
- どちらも `patch_flowforge_flow` で了承済みの変更だけを反映し、`verified=true`、構造は変わらず
- 細部の表示の不整合は残るが、追加の実装は優先しない
