# 作業フローと実装用プロンプトを作るための共通依頼

以下の業務について、まず既存資産を確認し、私との会話で作業フローを磨いてください。フローが固まったら、FlowForgeの「エージェントへの指示」のように、Codex・Claude Code（ミスレモン）・GenCode等へそのまま渡せる実装用プロンプトを出してください。FlowForge自体を経由する必要はありません。

業務名・目的: 今回の依頼内容から具体化する。
既存資料・作業場所: 与えられた資料や参照可能な既存リポを必要範囲で確認する。

## フローを作る時の要件

- 各ノードに「人間／AI／プログラム／外部ツール」の主体ラベルと、実際に動く担当・道具を見える形で表示し、凡例を付ける。AIはチャッピー・Codex・ミスレモン・GenCode等、プログラムはスクリプト名、外部ツールはサービス名と確認済みの利用方法を明記。未定は未定と表示する。
- 主体と利用先を区別する。例：「プログラム｜Python xxx.py → Supabase｜数値保存」。AIが書いたプログラムでも、実行時にAIを呼ばなければプログラムと表示。
- 各工程のトリガー、入力、処理、保存先、画面反映先、報告先、成功・部分成功・失敗を明示。
- 既存／未実装／未確認、確定事項／提案を区別。
- 判断が必要な場所は、判断事項・おすすめ・理由・保留した場合の扱いを表示。
- 今回の取り直しと次回の改善を分け、それぞれの戻り先へ条件付きの矢印を描く。
- 判断と本人の理由を記録する保存先、次回開始時に有効な採用基準を取得する処理、適用IDと結果を照合する仕組みを明文化。
- Slackは報告の出口を基本とし、依頼・フィードバックは音声/チャット。入口を変える場合は私と決める。

## フロー確定後に出してほしい実装用プロンプトの型

以下の構成を今回の具体的な内容で埋める。実装する工程数に合わせ、不要な節や未定の仮値を残さない。

### 業務自動化・社員具体化の依頼

対象業務、既存社員の有無、作業場所、依頼する実装担当を明記する。既存資産を再利用し、簡単な段階から実装する旨を記載。

### 目的・背景

実現したい結果、現状の問題、すでに調べたことを圧縮して記載。不要な再調査を避ける。

### 優先する確定事項と未確認事項

利用者と合意した運用・道具・保存・報告・権限を明記。未確認のAPIや連携、未実装の仕組みを区別。一般テンプレートを理由に合意済み方針を変更しない。

### 開始トリガー

定期、本人依頼、イベントなど、今回の入口と重複時・起動できなかった時の扱いを明記。

### 各工程

フローと同じ番号・名前・主体ラベル（人間/AI/プログラム/外部ツール）で、実際に動くAIや人の担当・スクリプト名・利用サービス・確認済みの接続方法、処理、入力、出力・保存先、成功/失敗、人の判断条件を記載。主体と利用先を分け、未定・未実装を明示。

### 接続・分岐・戻り先

通常の接続、条件分岐、未取得分の再実行、判断後の復帰、次回の基準取得を列挙。戻り条件、対象範囲、停止条件を明記し、無条件の自動反復を避ける。

### 判断ログとフィードバック

保存先、判断事項、AI案、本人選択、本人の理由、対象、今回だけ/次回基準、期限・取消・改定、run_idを記録。未判断や見送りを採用扱いにしない。次回に有効な採用基準だけ取得し、適用IDと結果を追跡。読取・保存失敗時の扱いも定義。

### 成果物・反映・報告

データ保存先、画面の参照先、報告の出口を区別。保存済みと画面反映確認済みを別に判定。報告に載せる/載せない情報と、部分成功時の伝え方を決める。

### 変更範囲・実装順序

既存処理を活かす最小の段階から始める。フローにAIと書かれていても、機械判定できる箇所はコードを使える。追加従量課金APIや別スケジューラを無断で必須にしない。

### 受け入れ条件・検証

正常系、部分失敗、重複起動、ログ取得/記録失敗、採用/今回だけ/取消/期限切れ、権限、画面反映のうち該当する項目を観測可能な条件で記載。

### 参考資料・安全ルール

関連ファイルと確認済み内容を示す。既存AGENTS/CLAUDEを尊重。秘密を出力せず、外部送信・削除・公開・契約・送金・課金変更・本番有効化は今回の明示了承範囲に限定。

### 最初の返答と完了報告

最初は、環境と既存資産の確認、3〜4段階の短い実装計画、最初に作る具体的なもの・完了条件を提示。人への依頼は必要なものだけ番号付きで分ける。不要なアカウント開設・再接続を求めない。
完了時は、変更内容、検証結果、未完了・未検証、次の一手を短く報告し、正本の手順・作業記録も更新。設計・実装・本番稼働を混同しない。
