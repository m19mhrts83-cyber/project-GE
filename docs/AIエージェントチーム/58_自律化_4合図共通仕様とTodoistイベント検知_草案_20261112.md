## 結論（案）

1. **合図の言葉は既存の4種をそのまま共通語にする**（新しく作らない）: `human`（人が頼む）／`schedule`（時間）／`event`（何かが届いたら）／`watch`（変化・失敗を見回ったら）
2. **Todoist の変更検知は Webhook を本線**にする。すでに Vercel `/api/todoist/webhook` → Supabase `todoist_webhook_events` が動いている（署名検証あり）。**ポーリングは取りこぼしの補完だけ**（1日1回の差分照合）
3. 新しい常駐の仕組みは作らず、**317 の拾い（L1）にイベント種別を足す**形で広げる

## Webhook とポーリングの比較

| 観点 | Webhook（本線案） | 定期ポーリング |
|---|---|---|
| 速さ | 数秒で受信。処理は 317 の5分間隔 | 間隔しだい（5分〜） |
| 費用 | 0円（Vercel Hobby・Supabase 無料枠） | API 呼び出しが増える。Mac か GHA の枠を使う |
| 取りこぼし | Vercel 停止・署名不一致で落ちうる | 間隔内の中間状態は見えない |
| 既存 | **あり**（note:added・item:completed を処理中） | `jarvis_watch_todoist_sync.py`（監視用） |
| 結論 | 本線 | 補完（日1回、Webhook に無い変更だけ拾う） |

## イベント1件の共通の形

どの合図でも、次の項目を持つ行として扱う（置き場は下の「決めてほしいこと 2」）。

| 項目 | 内容 |
|---|---|
| `event_id` | `<source>:<元のID>`（例 `todoist:note:12345`）。**重複判定キー** |
| `kind` | human／schedule／event／watch |
| `source` | todoist／slack／gmail／gha／launchd 等 |
| `occurred_at` | 起きた時刻 |
| `ref` | 元のタスク・スレ・メールへのリンク |
| `status` | new → claimed → done／failed／skipped |
| `claimed_by` | 担当（社員番号＋ツール名） |
| `attempts`・`last_error` | 再試行の回数と最後の失敗 |

## Gmail 着信の合図（案・2026-11-15 Miss Lemon）

Todoist `6hwmh986wHvjj7wv`「Gmail到着イベントの自動タスク化を既存317/comm hubと整合して設計」の仕様案。**未承認**。

### 今あるもの（二重に作らない）

| 段 | 既存 | 時刻 |
|---|---|---|
| 取得・判定 | GHA `jarvis-dashboard-gmail-triage.yml`（admin 差分トリアージ → `triage_items`／パートナー未返信 → `triage_items`／bot 通知 → `comm_items`） | 毎日 05:00 |
| 取得・判定（Mac） | launchd `night-triage`（`jarvis_night_triage.py`） | 毎日 05:xx |
| 人に見せる | 116 メール要対応 → Slack `#consult`（ボタン） | 判定のあと |
| Todoist 化 | ボタン「Todoist」→ `createTodoistTask`（`[メール要対応]`／`[資料待ち]`・`返信待ち`・期日+2日・同名の開いたタスクがあれば作らない） | 人が押したとき |

つまり **Gmail → Todoist はもうある**。足りないのは「1日1回で遅い」「人がボタンを押すまでタスクにならない」の2点。

### 案

1. **新しい受信の仕組みは作らない**。GAS 10分ポーリング・Gmail Push（Pub/Sub）は使わない（317 の「やらないこと：GAS ポーリング」、Pub/Sub は常駐の受け口が要る）
2. 速さは **既存の GHA トリアージを日中にも回す**ことで出す（例: 05:00 に加え 9〜21時の2時間おき。差分トリアージなので重複は `triage_items.id` の upsert で吸収）
3. Todoist 化は **自動にするのは条件を満たすものだけ**。条件（すべて満たす）:
   - lane が partner／general の **人からのメール**（bot・通知・ミュート済み差出人は除外。116 の除外規則をそのまま使う）
   - 116 の判定が「要対応」
   - 同じ `gmail_thread_id` の開いた Todoist タスクが無い（あればコメントで足す＝58_ の「312 との重複回避」）
   - それ以外はこれまでどおり `#consult` のボタン
4. 共通の形（上の表）への当てはめ: `event_id = gmail:<gmail_message_id>`／`kind = event`／`source = gmail`／`ref = Gmail スレ URL`。置き場は `triage_items` に列を足す（決定2 (A) と同じ。段階1と同じ形の migration）
5. 起票は **312 経由**（`createTodoistTask` の重複確認つき）。期日はこれまでどおり +2日で 313 の朝処置に乗る
6. 停止: `GMAIL_EVENT_DISABLE=1`（自動起票だけ止め、ボタンは残す）。夜間 0:00〜6:00 は自動起票しない
7. 権限: **読み取りと下書きまで**。返信の送信は別の了承（今と同じ）
8. 誤検知の見方: 自動起票したタスクに `auto_gmail` ラベル。週次 314 で「人が即やめた率」を見る（owner_decisions と同じ考え）

### 検証と実装（2026-11-15 Claude・317 スレッド）

- 過去2週間の triage_items（kind=mail・partner/general 約40件）に自動起票の条件を当てた。ボタンで Todoist 3件／返信 13件／見送り 20件。116 スコアは ACTION_RE（「お願い」「ご確認」等）でほぼ全件上がり、御礼メール・フォーム自動返信も通る。資料依頼・TODO 語で絞ると署名の電話番号や御礼文を拾い、本当の依頼（募集依頼書の記入）を落とす → **ルールだけの自動起票は精度不足で保留**（AI 判定は従量課金ゼロ方針で入れない）
- 代わりに **決めてほしいこと 2 の日中取込だけ実装**（おすすめ・松野さん判断待ち。PR 下書き）:
  - GHA `jarvis-dashboard-gmail-triage` に日中便 `0 0-12/2 * * *`（9〜21時 JST・2時間おき）。general 取込だけ、`--new-only --no-mark-read --no-digest --lookback-days 2`
  - `--new-only`: id か gmail_message_id が既にある行は触らない（upsert で payload の Slack 投稿済み印が消えるのを防ぐ）
  - 日中便の heartbeat は `comm_write_day`（本便 `comm_write` を上書きしない＝予備の代走判定を変えない）
  - 止める: リポジトリ変数 `JARVIS_GMAIL_DAYTIME_DISABLE=1`
